# Feature Specification: Effective DB User Storage, APP_MODE Selector & Production Wiring Foundation (Fase 5 foundation)

**Feature Branch**: `007-production-db-wiring`

**Created**: 2026-09-01

**Status**: Draft

**Input**: User description: "Effective DB user storage + APP_MODE selector + production wiring foundation. This spec ensures that users, face templates, and sessions are effectively stored and retrieved from the real PostgreSQL database in production mode, and introduces the configuration-driven adapter selector (APP_MODE=production|mock) that all subsequent Fase 5 specs (008 concrete ML adapters, 009 concrete mood/age adapters) build on. It covers the 'effective store users on db' requirement and lays the wiring foundation for PRD §18 Fase 5. Currently, the app always wires mock adapters (main.wire_mock_adapters) — in-memory repositories that lose data on restart. The real SQLAlchemy adapters (adapters/db/repositories.py: SqlAlchemyUserRepository, SqlAlchemyFaceTemplateRepository, SqlAlchemySessionManager, SqlAlchemyUnitOfWork) already exist from spec 001 and are used in integration tests, but they are never wired into the production app. This spec: (1) Introduces APP_MODE setting (env var APP_MODE=production|mock, default mock for dev/demo safety) in config.py Settings. (2) Creates a production wiring function wire_production_adapters() in main.py that wires the real SQLAlchemy DB adapters (UserRepository, FaceTemplateRepository, SessionManager, UnitOfWork) to PostgreSQL, while still using the mock ML adapters (Detector, Embedder, AgeEstimator, MoodEstimator) — because real ML models come in specs 008/009. This gives a working production app with real persistence but mock ML. (3) Creates a selector function select_wiring(app_mode) that returns either mock or production wiring based on APP_MODE. (4) Updates the FastAPI app factory to call the selector at startup. (5) Ensures the database session factory (async SQLAlchemy engine + sessionmaker) is properly created from DATABASE_URL for production mode. (6) Ensures Alembic migrations run (or are documented to run) before the app starts in production. (7) Adds integration tests that verify users/templates/sessions persist across requests in production mode (using a real PostgreSQL test container or test transaction). (8) Updates docker-compose.yml to ensure PostgreSQL is healthy before the backend starts and DATABASE_URL is correctly configured. Scope boundaries: IN: APP_MODE config, wire_production_adapters() (real DB repos + mock ML adapters), select_wiring selector, DB session factory for production, app factory update, integration tests for production persistence, docker-compose healthcheck ordering. OUT: Concrete ML adapters (specs 008/009), model download/cache, frontend changes, new endpoints, changes to domain ports/entities, changes to mock adapters (retained verbatim), changes to existing domain/contract/unit tests (they keep using mocks). Map to PRD: §18 Fase 5 foundation, §11 backend requirements (DB persistence), Constitution Principles IV (Docker), VI (PostgreSQL), VII (hexagonal — production wiring selects adapters at composition time)."

Rationale: the demo's primary path is the mock-mode runnable stack from spec 001; flipping the default to `production` would surprise local developers and break the existing domain/contract/unit tests that assume mock wiring (those tests are explicitly out of scope to change). `APP_MODE=production` is an opt-in that the docker-compose production service sets explicitly. This preserves backward compatibility with specs 001-006.
- Q: In production mode, which adapters are real and which stay mock? -> A: The four **persistence adapters** are real SQLAlchemy implementations wired to PostgreSQL: `UserRepository`, `FaceTemplateRepository`, `SessionManager`, `UnitOfWork` (all pre-existing from spec 001, reused verbatim — not re-created). The four **ML adapters** stay mock: `Detector`, `Embedder`, `AgeEstimator`, `MoodEstimator` (the exact same mock instances `wire_mock_adapters` produces). Rationale: real ML models are explicitly deferred to specs 008/009 (scope boundary). The docker-compose backend service depends on PostgreSQL with a `healthy` condition, and the entrypoint runs migrations once the DB is reachable, then starts the app. A documented manual fallback (`make migrate` / `alembic upgrade head`) is provided for host-native runs. Rationale: Constitution Principle VI states "migrations run as part of container startup or a documented `make migrate` step"; the entrypoint approach satisfies "as part of container startup" and keeps `docker compose up` the canonical one-command path (Principle IV). Rationale: Constitution Quality Gate §6 mandates "at least one integration test per user story exercising the real adapters (PostgreSQL + filesystem) via `docker compose`." A real container is chosen over an in-memory substitute or a single test transaction because the spec's core claim is *real cross-request persistence* — only a real PostgreSQL demonstrates that. A single test transaction would defeat the purpose (it rolls back, hiding whether data truly committed). The existing domain/contract/unit tests are untouched (they keep using mocks — scope boundary).
- Q: Does `select_wiring` run at startup (composition time) or per-request? -> A: **At startup (composition time), once.** The app factory reads `APP_MODE` from settings, calls `select_wiring(app_mode)` once, and the resulting adapter set is wired into the app's dependency container for the lifetime of the process. Rationale: Constitution Principle VII — "concrete models are adapters selected at composition time." Per-request selection would be a runtime anti-pattern in hexagonal architecture and would complicate the dependency container for no demo value (Principle I — YAGNI).
- Q: What happens if `APP_MODE=production` but `DATABASE_URL` is unset or the DB is unreachable? -> A: The app **fails fast at startup** with a clear, actionable error (e.g. "APP_MODE=production requires a reachable DATABASE_URL; got <value>"). The startup sequence is: load settings → if `APP_MODE=production`, validate `DATABASE_URL` is set → create the async engine/sessionmaker → run migrations (which require connectivity) → wire production adapters → build app. A missing/unreachable DB surfaces during migration or engine creation and stops the process before it serves traffic. Rationale: failing fast is the demo-grade behavior that makes a misconfigured production start immediately obvious; silently falling back to mock would hide the misconfiguration and violate the spec's intent.
- Q: Is the mock wiring path (`wire_mock_adapters`) changed by this spec? -> A: **No.** `wire_mock_adapters` and the mock adapters themselves are retained verbatim (scope boundary). `select_wiring("mock")` returns the same mock wiring the app uses today. The only change to the app factory is that it now calls `select_wiring(settings.app_mode)` instead of calling `wire_mock_adapters()` directly — when `APP_MODE` is unset/mock, behavior is identical to specs 001-006. This guarantees the existing domain/contract/unit tests (which assume mock wiring) keep passing without modification.
- Q: Does this spec introduce any new endpoint, domain entity, or port? -> A: **No.** No new HTTP endpoints, no new domain entities, no new ports, no changes to existing ports or entities (scope boundary). The spec is pure composition/wiring: it selects between two already-existing adapter sets and ensures the real DB session factory is constructed from `DATABASE_URL`. The `User`, `FaceTemplate`, `AuthSession` entities and their repositories/session-manager/unit-of-work ports are all pre-existing from specs 001-003 and are reused as-is.
- Q: Does this spec change the frontend? -> A: **No.** Frontend changes are explicitly out of scope (scope boundary). The frontend is unaware of `APP_MODE`; it talks to the same HTTP contracts (PRD §8) regardless of wiring. In production mode the backend persists data for real, but the API surface is identical.
- Q: What does "persist across requests" mean for the integration tests, and is an app-restart assertion required? -> A: "Persist across requests" means: data written by one HTTP request (e.g. onboarding creating a `User` + `FaceTemplate`) is retrievable by a later, independent HTTP request (e.g. face-login reading the `FaceTemplate`, `GET /api/auth/me` reading the `AuthSession`) backed by PostgreSQL — not an in-memory store. A **cross-restart persistence assertion is included as a strong signal**: the tests stop the app process, restart it against the same PostgreSQL, and confirm previously-stored rows are still retrievable (this is the definitive proof that persistence is real and not in-process memory). If a clean process-restart proves impractical in the test harness, the tests at minimum assert the rows exist directly in PostgreSQL via an out-of-band DB inspection after the writing request, which already distinguishes real persistence from in-memory. The cross-restart assertion is the preferred, stronger form.

### Session 2026-09-01 (clarify gate)

- Q: What form must `DATABASE_URL` take, and is it validated as an async SQLAlchemy URL? -> A: `DATABASE_URL` MUST be an async SQLAlchemy connection string (e.g. `postgresql+asyncpg://user:password@host:5432/dbname`); the `Settings` loader accepts it as-is and validation is performed implicitly at engine creation — a malformed or sync-only scheme (e.g. `postgresql://` without the `+asyncpg` driver) surfaces as a fail-fast startup error during engine/sessionmaker construction (FR-006), before any traffic is served. Rationale: the spec mandates an *async* engine + sessionmaker (FR-006); a sync URL would produce a runtime TypeError at first use rather than a clear startup failure. Treating engine creation as the validation step avoids introducing a separate URL-parsing concern (YAGNI, Constitution Principle I) and keeps the fail-fast path unified with the unreachable-DB path already specified.
- Q: What does the backend health endpoint report in each mode, and does mock mode assert DB connectivity? -> A: In `mock` mode the health endpoint reports healthy with **no** DB-connectivity check (no DB is configured or required — FR-003). In `production` mode the health endpoint reports healthy **with** a DB-connectivity check (a lightweight `SELECT 1` / session-ping against the wired engine); a failed DB ping reports unhealthy. Rationale: the health endpoint is the compose healthcheck's signal (FR-010); requiring a DB ping in mock mode would force a PostgreSQL dependency that the spec explicitly eliminates for mock (FR-003), and omitting it in production would hide DB outages from the orchestrator. This pins a per-mode behavioral contract that the startup and selector tests (FR-014c) can assert without introducing a new endpoint (the health endpoint is pre-existing from spec 001).

### User Story 1 - Real Persistence of Users, Templates & Sessions in Production Mode (Priority: P1)

When the application is started in production mode (`APP_MODE=production`) against a reachable PostgreSQL database, onboarding creates a real `User` and `FaceTemplate` row in PostgreSQL, face-login reads the stored `FaceTemplate` and creates a real `AuthSession` row, and `GET /api/auth/me` reads the stored session — all backed by the database, not in-process memory. Data written by one request is retrievable by a later, independent request, and survives an application process restart (the definitive proof that persistence is real). This is the "effective store users on db" requirement: users, face templates, and sessions are effectively stored and retrieved from the real PostgreSQL database in production mode (PRD §11, Constitution Principle VI).

**Why this priority**: This is the core deliverable and the reason the spec exists. Without real persistence in production mode, the app loses all data on restart and the demo cannot show a realistic 1:1 verification flow backed by a real RDBMS (Constitution Principle VI — "a real RDBMS makes the 1:1 verification lookup realistic"). It delivers PRD §11 ("procesamiento facial debe ejecutarse en el servidor") and the persistence foundation that specs 008/009 (real ML) will plug into. Every other story in this spec exists to make this one correct and safe.

**Independent Test**: Start the app with `APP_MODE=production` against a fresh PostgreSQL test container. Perform onboarding via `POST /api/onboarding` (creates `User` + `FaceTemplate`); perform face-login via `POST /api/auth/face-login` (reads the `FaceTemplate`, creates `AuthSession`); call `GET /api/auth/me` (reads the `AuthSession`). Inspect PostgreSQL out-of-band and assert the `User`, `FaceTemplate`, and `AuthSession` rows exist. Stop the app process, restart it against the same PostgreSQL, and call `GET /api/auth/me` with the old session cookie — assert it still resolves to the same user (cross-restart persistence). Delivers a verifiable, real-persistence production app.

**Acceptance Scenarios**:

1. **Given** the app is started with `APP_MODE=production` and a reachable PostgreSQL, **When** onboarding is performed via `POST /api/onboarding`, **Then** a `User` row and a `FaceTemplate` row are committed to PostgreSQL and retrievable out-of-band (PRD §11, Constitution Principle VI).
2. **Given** a `User` and `FaceTemplate` exist in PostgreSQL, **When** face-login is performed via `POST /api/auth/face-login` with a matching capture, **Then** the backend reads the stored `FaceTemplate` from PostgreSQL (not in-memory) and, on a successful match, creates an `AuthSession` row in PostgreSQL.
3. **Given** an `AuthSession` exists in PostgreSQL, **When** `GET /api/auth/me` is called with the session cookie, **Then** the backend reads the session from PostgreSQL and returns the authenticated state.
4. **Given** data was written by a prior request, **When** a later, independent request reads it, **Then** the data is retrievable because it was committed to PostgreSQL (not held in process memory).
5. **Given** the app has stored a `User`, `FaceTemplate`, and `AuthSession` in PostgreSQL, **When** the app process is stopped and restarted against the same PostgreSQL, **Then** the previously-stored rows are still retrievable and `GET /api/auth/me` with the old session cookie still resolves to the same user (cross-restart persistence — the proof that persistence is real).

### User Story 2 - APP_MODE Configuration Selector (Priority: P2)

The application selects its adapter wiring at startup based on a single configuration setting, `APP_MODE`, read from the environment (`APP_MODE=production|mock`). When `APP_MODE=mock` (or unset), the app wires the mock adapters — the exact same in-memory wiring the app uses today (specs 001-006 behavior, unchanged). When `APP_MODE=production`, the app wires the real SQLAlchemy database adapters for persistence while keeping the mock ML adapters. The selection happens once at composition time (Constitution Principle VII), not per-request. This makes the demo's adapter choices configuration-driven and gives subsequent specs 008/009 a single, stable selector to extend.

**Why this priority**: The selector is the wiring foundation the feature description centers on and the seam specs 008/009 build on. It delivers Constitution Principle VII ("concrete models are adapters selected at composition time") and PRD §19's open question "si el modo demo permitirá usar mocks mediante configuración" (resolved: yes, via `APP_MODE`). It is independently testable by starting the app in each mode and inspecting which adapter set is wired.

**Independent Test**: (a) Start the app with `APP_MODE` unset; assert the wired repositories are the in-memory mock instances and no PostgreSQL connection is required. (b) Start the app with `APP_MODE=production` and a reachable PostgreSQL; assert the wired repositories are the real SQLAlchemy implementations and the ML adapters are still the mock instances. (c) Start with `APP_MODE=invalid`; assert a clear startup error. Delivers a configuration-driven wiring selector with both modes verifiable.

**Acceptance Scenarios**:

1. **Given** `APP_MODE` is unset or set to `mock`, **When** the app starts, **Then** it wires the mock adapters (in-memory repositories + mock ML) and behaves identically to specs 001-006 (backward compatible).
2. **Given** `APP_MODE=production` and a reachable PostgreSQL, **When** the app starts, **Then** it wires the real SQLAlchemy database adapters (UserRepository, FaceTemplateRepository, SessionManager, UnitOfWork) for persistence and the mock ML adapters (Detector, Embedder, AgeEstimator, MoodEstimator) for vision.
3. **Given** the app is starting, **When** the selector runs, **Then** it runs exactly once at composition time and the chosen adapter set is fixed for the lifetime of the process (Constitution Principle VII).
4. **Given** `APP_MODE` is set to an unrecognized value, **When** the app starts, **Then** it fails fast with a clear, actionable error listing the allowed values (`production`, `mock`).
5. **Given** `APP_MODE=production` but `DATABASE_URL` is unset or the database is unreachable, **When** the app starts, **Then** it fails fast at startup with a clear error indicating production mode requires a reachable database, before serving any traffic.

### User Story 3 - Production Startup: DB Session Factory, Migrations & Compose Healthcheck Ordering (Priority: P3)

In production mode, the application constructs its database session factory (an async SQLAlchemy engine and sessionmaker) from the `DATABASE_URL` configuration setting, runs Alembic migrations to head as a pre-start step (gated on `APP_MODE=production`) before the app process begins serving, and the docker-compose production stack ensures PostgreSQL is healthy before the backend service starts and that `DATABASE_URL` is correctly configured for the backend container. `docker compose up` remains the canonical one-command path to a working production stack (Constitution Principle IV).

**Why this priority**: This is the operational foundation that makes User Story 1 possible in the containerized demo: without a correctly-constructed session factory, applied migrations, and correct service ordering, the production app cannot reach or persist to PostgreSQL. It delivers Constitution Principles IV (Docker) and VI (PostgreSQL — "migrations run as part of container startup or a documented `make migrate` step"). It is independently testable by bringing up the compose stack and confirming the backend starts only after PostgreSQL is healthy and the schema is migrated.

**Independent Test**: Run `docker compose up` (or the production compose profile) from a clean state; observe that the backend service waits on PostgreSQL's healthy condition before starting, that migrations apply to the database before the app accepts traffic, and that `DATABASE_URL` in the backend container points to the compose PostgreSQL service. Then confirm the backend health endpoint reports healthy with DB connectivity. Delivers a correctly-ordered, migrated, containerized production startup.

**Acceptance Scenarios**:

1. **Given** `APP_MODE=production`, **When** the app starts, **Then** it constructs the database session factory (async engine + sessionmaker) from `DATABASE_URL` and uses it for all persistence operations.
2. **Given** the production backend container is starting, **When** its entrypoint runs, **Then** it applies Alembic migrations to head against the target PostgreSQL before launching the app process (Constitution Principle VI).
3. **Given** migrations are not applicable (mock mode), **When** the app starts, **Then** no database connection or migration step is attempted.
4. **Given** the docker-compose production stack is brought up, **When** PostgreSQL is not yet healthy, **Then** the backend service does not start until PostgreSQL reports healthy (compose dependency with a healthy condition).
5. **Given** the compose stack is running, **When** the backend container's `DATABASE_URL` is inspected, **Then** it correctly points to the compose PostgreSQL service (host, port, database, credentials).
6. **Given** a developer running the backend host-native in production mode, **When** they follow the documented manual migration step, **Then** the schema is applied and the app starts (documented fallback per Constitution Principle VI).

2. **Given** the existing domain, contract, and unit test suites (specs 001-006), **When** they are run unchanged, **Then** they all pass (no test is modified by this spec).

### User Story 5 - Automated Production-Persistence & Wiring-Selector Tests (Priority: P5)

An automated test suite covers the production wiring foundation: integration tests that start the app with `APP_MODE=production` against a real PostgreSQL test container and verify that `User`, `FaceTemplate`, and `AuthSession` rows persist across independent HTTP requests and across an app process restart (User Story 1); selector tests that assert `mock` and `production` modes wire the correct adapter sets and that an invalid mode fails fast (User Story 2); startup tests that assert the DB session factory is constructed from `DATABASE_URL` and that migrations apply before serving in production mode (User Story 3); and a regression assertion that the existing domain/contract/unit suites still pass unchanged in mock mode (User Story 4). The domain/contract/unit portions run without GPU, network, or real models; only the production-persistence integration tests require a real PostgreSQL (provided by a test container).

**Why this priority**: Tests are the safety net that confirms production mode really persists to PostgreSQL (not in-memory), that the selector wires the correct adapters, and that mock mode is non-regressed (PRD §15, Constitution Quality Gates §5/§6/§7). It is independently testable by running the suite and by asserting a deliberate wiring regression (e.g. production mode silently using in-memory repositories) causes a test to fail.

**Independent Test**: Run the wiring test suite; assert all integration, selector, startup, and regression tests pass. Then introduce a deliberate regression (make `APP_MODE=production` wire in-memory repositories) and assert the production-persistence integration test fails. Delivers a green, reproducible wiring test foundation that catches persistence regressions.

**Acceptance Scenarios**:

1. **Given** the production-persistence integration tests, **When** they are run against a real PostgreSQL test container with `APP_MODE=production`, **Then** they assert `User`, `FaceTemplate`, and `AuthSession` rows persist across independent requests and across an app restart.
2. **Given** the selector tests, **When** they are run, **Then** they assert `mock` mode wires in-memory repositories + mock ML, `production` mode wires real SQLAlchemy repositories + mock ML, and an invalid mode fails fast.
3. **Given** the startup tests, **When** they are run, **Then** they assert the DB session factory is constructed from `DATABASE_URL` in production mode and migrations apply before the app serves traffic.
4. **Given** the regression assertion, **When** the existing domain/contract/unit suites are run unchanged in mock mode, **Then** they all pass.
5. **Given** a deliberate change making `APP_MODE=production` use in-memory repositories, **When** the production-persistence integration tests are run, **Then** at least one test fails (the cross-restart or out-of-band DB inspection assertion).
6. **Given** the domain/contract/unit portions of the suite, **When** they are run with no GPU and no network, **Then** they pass (Constitution Quality Gate §7).

### Edge Cases

- What happens when `APP_MODE` is unset? The app defaults to `mock` (dev/demo safety) and behaves identically to specs 001-006; no PostgreSQL is required.
- What happens when `APP_MODE` is set to an unrecognized value (e.g. `staging`, `prod`, empty string after trim)? The app fails fast at startup with a clear error listing the allowed values (`production`, `mock`).
- What happens when `APP_MODE=production` but `DATABASE_URL` is unset? The app fails fast at startup with an actionable error ("APP_MODE=production requires a reachable DATABASE_URL").
- What happens when `APP_MODE=production` and `DATABASE_URL` is set but the database is unreachable? The app fails fast during engine creation or migration execution with a connection error, before serving any traffic.
- What happens when migrations are already at head? The pre-start migration step is a no-op (Alembic reports "no new migrations") and the app starts normally.
- What happens when migrations are behind head? The pre-start migration step applies pending migrations to head before the app process starts; the app then starts against the updated schema.
- What happens when a migration fails mid-apply? The app does not start (the entrypoint exits non-zero); no partially-migrated app serves traffic. The failure is surfaced in the container logs.
- What happens when PostgreSQL becomes unhealthy after the backend has started? The app is already running; subsequent persistence operations fail at the port boundary and surface as recoverable `500 internal_error` responses (consistent with the error mapping in specs 002/003). Restoring PostgreSQL restores persistence without an app restart. This is a runtime resilience edge case, not a startup concern.
- What happens when the app is restarted in production mode against the same PostgreSQL? Previously-stored `User`, `FaceTemplate`, and `AuthSession` rows are still present (real persistence); `GET /api/auth/me` with an unexpired, non-revoked session cookie still resolves. This is the cross-restart persistence guarantee.
- What happens when the app is restarted in mock mode? All in-memory data is lost (the existing mock behavior, unchanged); this is expected and documented — mock mode is for dev/demo, not persistence.
- What happens if a developer changes a mock adapter in this spec? That is out of scope (scope boundary); mock adapters are retained verbatim. Any such change belongs in a separate spec.
- What happens if a developer changes a domain port or entity in this spec? That is out of scope (scope boundary); no ports or entities are added or altered. The spec is pure composition/wiring.
- What happens if a developer adds a new HTTP endpoint in this spec? That is out of scope (scope boundary); no new endpoints are introduced. The existing PRD §8 contracts are served identically in both modes.
- What happens if the frontend is modified in this spec? That is out of scope (scope boundary); the frontend is unaware of `APP_MODE` and talks to the same contracts in both modes.
- What happens when `select_wiring` is called more than once? It is called exactly once at composition time by the app factory; the result is cached for the process lifetime. Re-calling it is not supported and not needed (Constitution Principle VII — composition time, not per-request).
- What happens when the production-persistence integration tests run in an environment without Docker (no test container available)? The integration tests are skipped with a documented flag (consistent with Constitution Quality Gate §7 — "only the ML-adapter integration tests may need a model and may be skipped in CI with a documented flag"); the domain/contract/unit suites still run and pass.
- What happens when the docker-compose backend service starts before PostgreSQL is healthy? It does not — the compose dependency with a `healthy` condition prevents the backend from starting until PostgreSQL reports healthy.
- What happens when `APP_MODE=production` and `DATABASE_URL` is a sync-only scheme (e.g. `postgresql://` without `+asyncpg`)? The app fails fast at startup during async engine/sessionmaker construction with a clear error, before serving traffic (FR-006); engine creation is the validation step, so malformed URLs share the unified fail-fast path with unreachable-DB errors.
- What happens when the backend health endpoint is called in mock mode? It reports healthy with no DB-connectivity check (no DB is configured); in production mode it reports healthy with a lightweight DB ping (`SELECT 1`), and unhealthy if the ping fails (FR-010).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST support an `APP_MODE` configuration setting read from the environment with allowed values `production` and `mock`; when unset, it MUST default to `mock` (dev/demo safety, backward compatible with specs 001-006).
- **FR-002**: The system MUST provide a single wiring selector that, given the `APP_MODE` value, returns the complete adapter set for the app; it MUST run exactly once at startup (composition time) and the chosen adapter set MUST be fixed for the process lifetime (Constitution Principle VII).
- **FR-003**: When `APP_MODE=mock` (or unset), the selector MUST wire the mock adapters — the exact same in-memory repositories and mock ML adapters the app uses in specs 001-006 — and MUST require no PostgreSQL connection (backward compatible).
- **FR-004**: When `APP_MODE=production` and a reachable PostgreSQL is configured, the selector MUST wire the real SQLAlchemy database adapters for persistence (`UserRepository`, `FaceTemplateRepository`, `SessionManager`, `UnitOfWork`) and the mock ML adapters for vision (`Detector`, `Embedder`, `AgeEstimator`, `MoodEstimator`); no real ML adapter is introduced in this spec (scope boundary — real ML is specs 008/009).
- **FR-005**: When `APP_MODE` is set to an unrecognized value, the system MUST fail fast at startup with a clear, actionable error listing the allowed values (`production`, `mock`) and MUST NOT serve traffic.
- **FR-006**: When `APP_MODE=production`, the system MUST construct the database session factory (an async SQLAlchemy engine and sessionmaker) from the `DATABASE_URL` configuration setting and use it for all persistence operations; `DATABASE_URL` MUST be an async SQLAlchemy connection string (e.g. `postgresql+asyncpg://...`) — a malformed or sync-only scheme MUST surface as a fail-fast startup error during engine creation; if `DATABASE_URL` is unset or the database is unreachable, the system MUST fail fast at startup before serving traffic.
- **FR-007**: When `APP_MODE=production`, the system MUST apply Alembic migrations to head against the target PostgreSQL as a pre-start step before the app process begins serving; when `APP_MODE=mock`, no database connection or migration step MUST be attempted (Constitution Principle VI).
- **FR-008**: In production mode, onboarding MUST commit a real `User` row and a real `FaceTemplate` row to PostgreSQL; face-login MUST read the stored `FaceTemplate` from PostgreSQL and, on a successful match, commit a real `AuthSession` row; `GET /api/auth/me` MUST read the stored session from PostgreSQL. Data written by one request MUST be retrievable by a later, independent request (PRD §11, Constitution Principle VI).
- **FR-009**: In production mode, data persisted to PostgreSQL MUST survive an application process restart: after stopping and restarting the app against the same database, previously-stored `User`, `FaceTemplate`, and `AuthSession` rows MUST still be retrievable and a valid session cookie MUST still resolve (the definitive proof that persistence is real, not in-process memory).
- **FR-010**: The docker-compose production stack MUST ensure the backend service does not start until PostgreSQL reports healthy (dependency with a healthy condition) and MUST configure `DATABASE_URL` in the backend container to correctly point to the compose PostgreSQL service (Constitution Principle IV). The backend health endpoint MUST report healthy with a DB-connectivity check (lightweight `SELECT 1` / session-ping) in production mode and healthy with no DB check in mock mode (the endpoint is pre-existing from spec 001; no new endpoint is introduced).
- **FR-011**: `docker compose up` MUST remain the canonical one-command path to a working production stack; a documented manual migration step (e.g. `make migrate` / `alembic upgrade head`) MUST be provided for host-native production runs (Constitution Principles IV and VI).
- **FR-012**: The mock adapters, the mock wiring function, the domain ports, the domain entities, the HTTP contracts (PRD §8), and the frontend MUST be unchanged by this spec; no new endpoint, entity, port, or frontend change is introduced (scope boundary, Constitution Principle VII).
- **FR-013**: The existing domain, contract, and unit test suites (specs 001-006) MUST continue to pass without modification in mock mode (non-regression; scope boundary — existing tests are not changed).
- **FR-014**: An automated test suite MUST cover: (a) production-persistence integration tests using a real PostgreSQL test container that assert `User`/`FaceTemplate`/`AuthSession` persist across independent requests and across an app restart; (b) selector tests asserting `mock` and `production` wire the correct adapter sets and an invalid mode fails fast; (c) startup tests asserting the session factory is built from `DATABASE_URL` and migrations apply before serving in production mode; (d) a regression assertion that the existing domain/contract/unit suites pass unchanged in mock mode. The domain/contract/unit portions MUST run without GPU, network, or real models (PRD §15, Constitution Quality Gates §5/§6/§7).
- **FR-015**: The production-persistence integration tests MUST be skippable with a documented flag in environments without a real PostgreSQL available (e.g. no Docker); when skipped, the domain/contract/unit suites MUST still run and pass (Constitution Quality Gate §7).
- **FR-016**: No image, embedding, or biometric response MUST appear in application logs; observability is limited to structured JSON logs (startup mode selected, migration status, persistence operation duration/status) consistent with specs 001-006 and Constitution Principle VIII (PRD §12, §13). No audit log or immutable event store is required (Principle VIII — no traceability guarantee).
- **FR-017**: Concrete ML adapters (detector/embedder/age/mood models), model download/cache, frontend changes, new HTTP endpoints, changes to domain ports/entities, changes to mock adapters, and changes to existing domain/contract/unit tests are explicitly out of scope for this spec (scope boundary; real ML is deferred to specs 008/009).

### Key Entities *(include if feature involves data)*

- **User (from spec 002, unchanged)**: The registered person. In production mode, persisted to and retrieved from PostgreSQL via the real `UserRepository`. No new attributes; no schema change beyond what migrations already establish.
- **FaceTemplate (from spec 002, unchanged)**: The stored facial embedding. In production mode, persisted to and retrieved from PostgreSQL via the real `FaceTemplateRepository`. No new attributes.
- **AuthSession (from spec 003, unchanged)**: The authenticated session. In production mode, persisted to and retrieved from PostgreSQL via the real `SessionManager`. No new attributes.
- **APP_MODE setting (new configuration, not a domain entity)**: A process-level configuration value (`production|mock`, default `mock`) read from the environment at startup. Not persisted; it selects the adapter wiring at composition time. Not a domain entity — it lives in the application's configuration/settings, not the domain layer (Constitution Principle VII).
- **Database Session Factory (new infrastructure, not a domain entity)**: The async SQLAlchemy engine and sessionmaker constructed from `DATABASE_URL` in production mode. Infrastructure, not a domain entity; created at startup and shared by the real DB adapters.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: With `APP_MODE=production` against a real PostgreSQL, onboarding creates `User` + `FaceTemplate` rows, face-login creates an `AuthSession` row, and `GET /api/auth/me` reads the session — all from PostgreSQL, verifiable by out-of-band DB inspection after each request (PRD §11, Constitution Principle VI).
- **SC-002**: With `APP_MODE=production`, data persisted by one request is retrievable by a later, independent request, verifiable by performing onboarding then face-login as separate requests and confirming login succeeds against the stored template (FR-008).
- **SC-003**: With `APP_MODE=production`, persisted data survives an app process restart, verifiable by storing data, stopping and restarting the app against the same PostgreSQL, and confirming `GET /api/auth/me` with the old cookie still resolves (FR-009 — the definitive real-persistence proof).
- **SC-004**: With `APP_MODE` unset or `mock`, the app wires mock adapters, requires no PostgreSQL, and behaves identically to specs 001-006, verifiable by starting the app unset and exercising the existing flows (FR-003).
- **SC-005**: The selector wires the correct adapter set for each mode, verifiable by starting in `mock` and `production` modes and inspecting the wired repository/ML instances (FR-002, FR-003, FR-004).
- **SC-006**: An unrecognized `APP_MODE` value fails fast at startup with an actionable error, verifiable by starting with an invalid value and asserting the process exits before serving traffic (FR-005).
- **SC-007**: `APP_MODE=production` with unset/unreachable `DATABASE_URL` fails fast at startup, verifiable by starting with no `DATABASE_URL` and asserting a clear startup error (FR-006).
- **SC-008**: In production mode, the DB session factory is constructed from `DATABASE_URL` and migrations apply to head before the app serves traffic, verifiable by inspecting startup logs and the migrated schema (FR-006, FR-007).
- **SC-009**: The docker-compose backend service starts only after PostgreSQL is healthy and `DATABASE_URL` points to the compose PostgreSQL, verifiable by bringing up the stack and inspecting service ordering and the backend container's environment (FR-010).
- **SC-009a**: The backend health endpoint reports healthy with a DB-connectivity ping in production mode and healthy with no DB check in mock mode, verifiable by calling the health endpoint in each mode and inspecting whether the DB-ping branch is exercised (FR-010).
- **SC-010**: `docker compose up` brings up a working production stack with one command, verifiable by running it from a clean state and confirming the backend health endpoint reports healthy with DB connectivity (FR-011, Constitution Principle IV).
- **SC-011**: The mock adapters, domain ports, domain entities, HTTP contracts, and frontend are unchanged, verifiable by diffing the spec's changes against the specs 001-006 baseline (FR-012).
- **SC-012**: The existing domain, contract, and unit test suites pass unchanged in mock mode, verifiable by running them with no modifications (FR-013).
- **SC-013**: The production-persistence integration tests assert cross-request and cross-restart persistence against a real PostgreSQL test container, verifiable by running the integration suite and confirming the persistence assertions pass (FR-014).
- **SC-014**: A deliberate regression making `APP_MODE=production` use in-memory repositories causes at least one production-persistence integration test to fail, verifiable by introducing and reverting such a change (FR-014).
- **SC-015**: The domain/contract/unit portions of the suite pass with no GPU and no network, and the production-persistence integration tests are skippable with a documented flag when no PostgreSQL is available, verifiable by running under those constraints (FR-015, Constitution Quality Gate §7).
- **SC-016**: No image, embedding, or biometric response appears in logs; only structured JSON logs (mode selected, migration status, persistence duration/status) are produced, verifiable by inspecting startup and runtime logs (FR-016).
- **SC-017**: No concrete ML adapter, model download/cache, frontend change, new endpoint, domain port/entity change, mock adapter change, or existing-test change is introduced, verifiable by confirming the spec's scope excludes these (FR-017).

## Assumptions

- This spec builds directly on specs 001-006: the runnable stack, the four views, the seven HTTP contract endpoints (all implemented per specs 002-006), the domain entities (`User`, `FaceTemplate`, `AuthSession`), the hexagonal ports (user repository, face-template repository, session manager, unit of work, image storage, detector, embedder, age estimator, mood estimator), the mock adapters and the `wire_mock_adapters` composition function, the real SQLAlchemy adapters (`SqlAlchemyUserRepository`, `SqlAlchemyFaceTemplateRepository`, `SqlAlchemySessionManager`, `SqlAlchemyUnitOfWork`) pre-existing from spec 001 and used in integration tests, the PostgreSQL schema and Alembic migrations, the filesystem image-storage adapter, the FastAPI app factory, the `config.py` settings, and the `docker-compose.yml` stack are all assumed to exist and be reused, not re-created.
- The technology stack is fixed by the Constitution (Principle III / Technology Stack table): backend in Python with FastAPI, frontend in React with Vite, PostgreSQL for persistence, Alembic for migrations, Docker Compose for orchestration. These are project-level decisions, not ad hoc implementation choices, and are assumed settled for this spec.
- `APP_MODE` defaults to `mock` when the env var is unset, per the feature description ("default mock for dev/demo safety"). This preserves backward compatibility with specs 001-006, where the app always wires mock adapters. `APP_MODE=production` is an opt-in set explicitly by the docker-compose production service.
- In production mode, the four persistence adapters are real SQLAlchemy implementations (pre-existing from spec 001, reused verbatim) and the four ML adapters stay mock (the exact same mock instances `wire_mock_adapters` produces). Real ML models are deferred to specs 008/009 (scope boundary). This yields a working production app with real persistence but deterministic mock ML — the cleanest Fase 5 foundation slice.
- The wiring selector runs exactly once at startup (composition time), per Constitution Principle VII ("concrete models are adapters selected at composition time"). Per-request selection is a runtime anti-pattern in hexagonal architecture and is not used (Principle I — YAGNI).
- Alembic migrations run as a pre-start step in the backend container's entrypoint, gated on `APP_MODE=production`, once PostgreSQL is reachable. A documented manual fallback (`make migrate` / `alembic upgrade head`) is provided for host-native runs. This satisfies Constitution Principle VI ("migrations run as part of container startup or a documented `make migrate` step") and keeps `docker compose up` the canonical one-command path (Principle IV). Migrations are not run in mock mode (no DB required).
- The production-persistence integration tests use a real PostgreSQL test container (spun up per test session) and assert cross-request and cross-restart persistence of `User`/`FaceTemplate`/`AuthSession`. A real container is chosen over an in-memory substitute or a single test transaction because the spec's core claim is real cross-request persistence — only a real PostgreSQL demonstrates that, and a single transaction would roll back and hide whether data truly committed (Constitution Quality Gate §6). The existing domain/contract/unit tests are untouched (they keep using mocks — scope boundary).
- `APP_MODE=production` with unset or unreachable `DATABASE_URL` fails fast at startup with a clear, actionable error. The startup sequence is: load settings → validate `APP_MODE` → if production, validate `DATABASE_URL` → create engine/sessionmaker → run migrations → wire production adapters → build app. Failing fast makes a misconfigured production start immediately obvious; silently falling back to mock would hide the misconfiguration and violate the spec's intent.
- The mock wiring path (`wire_mock_adapters`) and the mock adapters are retained verbatim (scope boundary). The only change to the app factory is that it calls `select_wiring(settings.app_mode)` instead of `wire_mock_adapters()` directly; when `APP_MODE` is unset/mock, behavior is identical to specs 001-006. This guarantees the existing domain/contract/unit tests keep passing without modification.
- No new HTTP endpoints, domain entities, ports, or frontend changes are introduced (scope boundary). The spec is pure composition/wiring: it selects between two already-existing adapter sets and ensures the real DB session factory is constructed from `DATABASE_URL`. The frontend is unaware of `APP_MODE` and talks to the same PRD §8 contracts in both modes.
- The cross-restart persistence assertion (stop the app, restart against the same PostgreSQL, confirm data is still retrievable) is the preferred, stronger form of the persistence proof. If a clean process-restart proves impractical in the test harness, the tests at minimum assert rows exist via out-of-band DB inspection after the writing request, which already distinguishes real persistence from in-memory. The cross-restart form is preferred.
- Observability in this spec is limited to structured JSON logs (startup mode selected, migration status, persistence operation duration/status) with no images, embeddings, or biometric responses logged, consistent with specs 001-006 and Constitution Principle VIII (no traceability guarantee). No audit log or immutable event store is required.
- The docker-compose healthcheck ordering (backend waits on PostgreSQL healthy) and the correct `DATABASE_URL` configuration for the backend container are the operational changes in this spec; the compose file is the single source of truth for service topology (Constitution Principle IV). The `usuarios/` bind mount and other existing compose configuration are reused unchanged.
- Concrete ML adapters (specs 008/009), model download/cache, frontend changes, new HTTP endpoints, changes to domain ports/entities, changes to mock adapters, and changes to existing domain/contract/unit tests are explicitly out of scope for this spec.
- The real SQLAlchemy adapters from spec 001 are assumed to be correct and integration-tested (they are already used in integration tests per the feature description); this spec wires them into the production app, it does not re-implement or re-test their internal correctness.
