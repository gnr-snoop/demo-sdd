### Session 2026-08-31 (auto-resolved at specify gate)

- Q: Is the age estimation result persisted server-side (e.g. an `AnalysisRequest` audit row) or transient? -> A: Transient. The age result is NOT persisted server-side in this spec. PRD §7 marks `AnalysisRequest` as optional for the MVP and PRD §19 lists "Si los resultados de análisis se almacenarán o serán únicamente transitorios" as a pending decision; the demo-first Constitution Principle I and YAGNI rule out persisting audit rows that no acceptance criterion requires. The most recent age result lives in frontend state and remains visible until a new age analysis is triggered or the session ends (logout/expiry), per PRD §10 ("conservar los resultados visibles hasta que se ejecute un nuevo análisis o se cierre la sesión"). `AnalysisRequest` persistence is deferred to a later spec if a demo narrative need arises. This matches the transient decision already pinned in spec 004 (mood) for consistency.
- Q: Is `range` always present in the response, and how is `estimatedAge` related to it? -> A: Yes — the `200` response always includes `range: {min, max}` as integers (years), and `estimatedAge` as an integer (years) with `min <= estimatedAge <= max`. PRD §6.4 says the result is "una edad estimada en años o, preferentemente, como un rango de edad si el modelo lo permite"; PRD §8 shows all three fields. To keep the contract stable regardless of whether the age_estimator port produces a point estimate or a range, the backend normalizes the port output: if the port returns a range, `estimatedAge` is the midpoint (rounded to the nearest integer, clamped into `[min, max]`); if the port returns only a point estimate, the backend derives a symmetric range around it using a configurable half-width (default 5 years, clamped so `min >= 0`). The contract test asserts `estimatedAge`, `range.min`, `range.max` are integers and `min <= estimatedAge <= max` and `min >= 0`.
- Q: What is the exact `disclaimer` text? -> A: The fixed string from PRD §8: `"La edad es una estimación visual y puede contener un margen de error significativo."` It is returned verbatim by the backend on every `200` age response and rendered by the frontend alongside the result so the interface communicates the value is a visual estimation with a relevant error margin (PRD §6.4, §12 "No presentar edad o estado de ánimo como hechos ciertos").
- Q: What happens when the age capture contains no face or more than one face? -> A: The backend returns `400 Bad Request` with the actionable capture error body (`no_face` / `multiple_faces`) in the spec-002-pinned `{"error": {"code": "...", "message": "..."}}` shape, reusing the exact codes and status-code mapping established in specs 002/003/004. No age result is produced. This is consistent with FR-004 (validate capture) and FR-015 (actionable errors) and lets the person recapture. Identical to the mood behavior pinned in spec 004.
- Q: How is the age endpoint session-gated, and what does it return without a valid session? -> A: The real `require_valid_session` from spec 003 is reused (same as spec 004 mood). The endpoint rejects any request without a valid (non-expired, non-revoked, present) session with `401 unauthenticated` and performs no analysis. This replaces the spec 001 session-placeholder stub with real session enforcement (spec 003 FR-014).
- Q: In what order does the age endpoint evaluate conditions? -> A: (1) session validation via `require_valid_session` → `401 unauthenticated` if invalid; (2) decode + validate the image (format/size/long-edge, reusing spec 002 limits) → `400 invalid_image` if undecodable/unsupported/oversized; (3) run the detector port → `400 no_face` / `multiple_faces` / `insufficient_quality` if the capture is not exactly one usable face; (4) run the age_estimator port on the detected face → point estimate and/or range; (5) normalize to `{estimatedAge, range:{min,max}}` (midpoint/derived-range rule above); (6) return `200` with `{estimatedAge, range, disclaimer}`. A port/adapter error at step 3 or 4 returns a recoverable `500 internal_error` (actionable: "try again") and produces no result. Identical ordering to spec 004 mood, with the age_estimator port in place of mood_estimator.
- Q: How is FR-014 (no simultaneous invalid actions) implemented now that both mood and age are functional? -> A: The mood and age operations have **independent** loading/result/error state surfaces (PRD §6.4 — "Indicadores de carga independientes para cada operación", "Mensaje de error recuperable para cada operación"). However, the capture policy is **one capture at a time across the dashboard**: while either a mood or an age analysis is in flight, both the "Detectar estado de ánimo" and "Calcular edad" buttons are disabled and a second press of either is ignored (no second capture/request). This makes the FR-014 "una captura a la vez" MVP recommendation explicit and keeps the demo simple (one camera, one still at a time). Each button independently drives its own state machine and result/error surface; only the capture mutex is shared. No server-side single-analysis lock is added (demo-first); the frontend guard is the policy. This generalizes the spec 004 "one capture at a time" rule (where age was a disabled placeholder) to the now-enabled age button.
- Q: Is the age button rendered in this spec, and what happens to the spec 004 placeholder? -> A: The "Calcular edad" button already exists on `/dashboard` as a disabled placeholder with a "coming soon" indication (spec 004 FR-013). This spec **enables** it: the placeholder indication is removed, the button becomes keyboard-accessible and active, and pressing it triggers the age capture + `POST /api/analysis/age` flow. The dashboard layout (both buttons, camera preview, session indicator, logout) is unchanged from spec 004; only the age button's behavior and the age result/error/loading surfaces are added. This keeps the layout stable and avoids re-implementing mood.
- Q: Are real ML models used for age estimation? -> A: No. The age_estimator port is wired to the mock adapter from spec 001 for this entire spec. Real age models are explicitly deferred to Fase 5 (Constitution Principle VII; the port makes the swap a configuration change, not a redesign). The mock age estimator returns a deterministic point estimate and/or range for fixture inputs. This mirrors the spec 004 mood decision.
- Q: Is mood analysis re-implemented in this spec? -> A: No. Mood analysis is complete as of spec 004 and is explicitly out of scope here. This spec only adds the age flow and the shared capture mutex. The mood button, mood endpoint, mood result/error/loading surfaces, and mood tests from spec 004 are reused unchanged. The only change to mood behavior is the shared capture mutex: the mood button now also disables while an age analysis is in flight (and vice versa), per the FR-014 policy above.

### User Story 1 - Successful On-Demand Age Estimation (Happy Path) (Priority: P1)

A person with a valid session is on `/dashboard`. The camera preview is active. They press the keyboard-accessible "Calcular edad" button (previously a disabled placeholder from spec 004, now enabled by this spec). The frontend captures a single still image from the camera via standard browser media APIs (no continuous streaming), shows an independent loading indicator for age, disables both analysis buttons (FR-014 — one capture at a time), and sends the image as `multipart/form-data` to `POST /api/analysis/age` with the session cookie. The backend validates the session via the real `require_valid_session` (spec 003), decodes and validates the image (reusing spec 002 limits), runs the detector port and finds exactly one face, runs the age_estimator port to get a point estimate and/or range, normalizes to `{estimatedAge, range:{min,max}}`, and returns `200 OK` with `{estimatedAge, range, disclaimer}` per PRD §8. The frontend displays the age range (and point estimate), and the disclaimer text communicating this is a visual estimation with a significant error margin. The result remains visible until a new age analysis is triggered or the session ends.

**Why this priority**: This is the core age narrative and the primary deliverable of Fase 4's age portion. It delivers AC-008 (Edad) and exercises FR-011 (capture a single image) and FR-013 (calcular edad) end-to-end. Without a working age estimation the dashboard's second on-demand analysis value is absent and the MVP completion criterion (PRD §20 step 9) is unmet.

**Independent Test**: Perform a successful login (spec 003), then call `POST /api/analysis/age` with the session cookie and a fixture image the mock detector reports as exactly one face and the mock age estimator reports as point estimate `32` with range `[27, 37]`; assert a `200` response with `estimatedAge == 32`, `range.min == 27`, `range.max == 37`, `min <= estimatedAge <= max`, and the exact PRD §8 disclaimer string. Delivers a complete, demonstrable age estimation.

**Acceptance Scenarios**:

1. **Given** the person has a valid session and the camera is available, **When** they press "Calcular edad", **Then** the frontend captures a single still, shows the age loading indicator, disables both analysis buttons, and sends the image to `POST /api/analysis/age` with the session cookie (AC-008, FR-011).
2. **Given** a valid session and a capture containing exactly one face, **When** the backend processes the request, **Then** it returns `200 OK` with `estimatedAge` (integer), `range.min` and `range.max` (integers, `min >= 0`, `min <= estimatedAge <= max`), and the exact PRD §8 `disclaimer` string (FR-013, AC-008).
3. **Given** a successful age response, **When** the frontend receives it, **Then** it hides the loading indicator, re-enables the analysis buttons, and displays the age range and point estimate with the disclaimer text (PRD §6.4, §12).
4. **Given** an age result is displayed, **When** no new age analysis is triggered and the session remains valid, **Then** the result stays visible (PRD §10 — conservar resultados visibles hasta un nuevo análisis o cierre de sesión).
5. **Given** an age result is displayed, **When** the person triggers a new age analysis that succeeds, **Then** the displayed result is replaced with the new result.

### User Story 2 - Age Capture-Quality & Error Handling (Priority: P2)

When the age capture does not contain exactly one usable face, or the image cannot be decoded, or the age_estimator port raises an error, the backend returns an actionable error in the pinned `{"error": {"code": "...", "message": "..."}}` shape and produces no age result. Capture-quality failures (`no_face`, `multiple_faces`, `invalid_image`, `insufficient_quality`) return `400 Bad Request` with a message telling the person how to recapture; a port/adapter failure returns a recoverable `500 internal_error` (actionable: "try again"). The frontend shows the actionable error for the age operation with a retry option that does not require a full page reload, and re-enables the analysis buttons. The age error is independent from any mood error (separate error surfaces per PRD §6.4).

**Why this priority**: Actionable, recoverable errors are a PRD §6.4 / FR-015 requirement and keep the demo from dead-ending on a bad capture. It is independently testable by submitting each failure mode and asserting the correct actionable code, status, and that no age result is produced.

**Independent Test**: With a valid session, call `POST /api/analysis/age` with (a) an undecodable/oversized image → assert `400 invalid_image`; (b) a fixture image the mock detector reports as zero faces → assert `400 no_face`; (c) a fixture image the mock detector reports as two faces → assert `400 multiple_faces`; (d) a fixture image the mock detector reports as one face but flags insufficient quality → assert `400 insufficient_quality`; (e) a fixture triggering a port error → assert `500 internal_error`. In each case assert the body is the pinned error shape and no age result is returned. Delivers correct, actionable age error handling covering all four capture-quality codes.

**Acceptance Scenarios**:

1. **Given** a valid session, **When** the capture contains no face, **Then** the backend returns `400` with `code: "no_face"` and an actionable message indicating the person should recapture, and produces no age result (FR-004, FR-015).
2. **Given** a valid session, **When** the capture contains more than one face, **Then** the backend returns `400` with `code: "multiple_faces"` and an actionable message indicating only one person should appear, and produces no age result.
3. **Given** a valid session, **When** the image is undecodable, unsupported, or oversized, **Then** the backend returns `400` with `code: "invalid_image"` and an actionable message, and produces no age result.
4. **Given** a valid session, **When** the detector or age_estimator port raises an error, **Then** the backend returns `500` with `code: "internal_error"` and a recoverable message, and produces no age result.
5. **Given** an age error response, **When** the frontend receives it, **Then** it hides the loading indicator, re-enables the analysis buttons, and shows the actionable age error with a retry option that does not require a full page reload (FR-015, PRD §10).
6. **Given** the age_estimator returns only a point estimate (no range), **When** the backend normalizes it, **Then** the response includes a derived symmetric range around the estimate (default half-width 5 years, `min` clamped to 0) with `min <= estimatedAge <= max` (the person always gets a range per PRD §6.4).

### User Story 3 - Session Gating & Concurrent-Action Prevention on Age (Priority: P3)

The `POST /api/analysis/age` endpoint is protected by the real session validation from spec 003: a request without a valid (present, non-expired, non-revoked) session is rejected with `401 unauthenticated` and performs no analysis. On the frontend, the age button is disabled while an age analysis is in flight (FR-014) and a second press is ignored — one capture at a time. Because mood and age share a single camera, both buttons disable while either analysis is in flight (the capture mutex is shared), while their loading/result/error state surfaces remain independent. If the session expires or is revoked mid-analysis, the in-flight request receives `401 unauthenticated` and the frontend transitions to the unauthenticated state (redirect to `/login`), discarding any partial age result.

**Why this priority**: Session gating keeps the age endpoint behind the real session (FR-010, spec 003) and FR-014 prevents confusing concurrent captures. It is independently testable by attacking the endpoint without/with an invalid session and by attempting a double press or a cross-button press during an in-flight analysis.

**Independent Test**: Without a cookie, call `POST /api/analysis/age` → assert `401 unauthenticated` and no analysis. With an expired/revoked session → assert `401 unauthenticated`. With a valid session, trigger an age analysis and issue a second `POST /api/analysis/age` before the first resolves → assert the frontend ignores/disables the second press (one capture at a time). With a valid session, trigger an age analysis and press the mood button before the age analysis resolves → assert the mood button is disabled and the press is ignored (shared capture mutex). Delivers real session-gated, non-concurrent age analysis.

**Acceptance Scenarios**:

1. **Given** no valid session, **When** `POST /api/analysis/age` is called, **Then** it returns `401 unauthenticated` and performs no analysis (FR-010, spec 003).
2. **Given** an expired or revoked session, **When** `POST /api/analysis/age` is called, **Then** it returns `401 unauthenticated` and performs no analysis.
3. **Given** an age analysis is in flight, **When** the person presses the age button again, **Then** the button is disabled and the second press is ignored — no second capture or request is initiated (FR-014, one capture at a time).
4. **Given** an age analysis is in flight, **When** the person presses the "Detectar estado de ánimo" button, **Then** the mood button is disabled and the press is ignored — no concurrent capture is initiated (FR-014, shared capture mutex).
5. **Given** an age analysis is in flight, **When** the session expires or is revoked before the response, **Then** the response is `401 unauthenticated`, the frontend discards any partial age result, and transitions to the unauthenticated state (redirect to `/login`).
6. **Given** an age analysis completes (success or error), **When** it finishes, **Then** both analysis buttons are re-enabled and a new analysis (mood or age) can be triggered.

### Edge Cases

- What happens when the capture contains no face or more than one face during an age analysis? The backend returns `400 no_face` / `multiple_faces` with an actionable recapture message and produces no age result (FR-004, FR-015).
- What happens when the capture contains exactly one face but the detector flags it as unusable (too small/blurry/below quality threshold)? The backend returns `400 insufficient_quality` with an actionable recapture message and produces no age result — distinct from the face-count and decode failures (FR-006, FR-015). The integration test suite exercises this path via a fixture that makes the mock detector flag insufficient quality.
- What happens when the age_estimator port returns only a point estimate (no range)? The backend derives a symmetric range around the estimate (default half-width 5 years, `min` clamped to 0) and returns `200` with `{estimatedAge, range, disclaimer}`; the person always gets a range per PRD §6.4.
- What happens when the age_estimator port returns a range but no point estimate? The backend sets `estimatedAge` to the midpoint of the range (rounded, clamped into `[min, max]`) and returns `200` with all three fields.
- What happens when the derived/returned range has `min < 0`? The backend clamps `min` to 0 (age cannot be negative); `estimatedAge` is clamped into `[min, max]` accordingly.
- What happens when the detector or age_estimator port raises an error? The backend returns a recoverable `500 internal_error` (actionable: "try again") and produces no age result; no partial result is shown.
- What happens when the session expires or is revoked while an age analysis is in flight? The in-flight request receives `401 unauthenticated`; the frontend discards any partial age result and transitions to the unauthenticated state (redirect to `/login`).
- What happens when the person presses the age button twice rapidly? The button is disabled on the first press; the second press is ignored — one capture at a time, no second request (FR-014).
- What happens when the person presses the mood button while an age analysis is in flight? The mood button is disabled (shared capture mutex); the press is ignored — no concurrent capture (FR-014).
- What happens when the camera stream ends or the permission is revoked mid-capture? The UI transitions to a recoverable age error state with an actionable message and a retry option (PRD §10).
- What happens when the image is valid but exceeds the size/format/long-edge limits? The backend returns `400 invalid_image` and produces no age result (reusing spec 002 limits, Constitution OQ-8).
- What happens when the age endpoint is called without a session cookie? The backend returns `401 unauthenticated` and performs no analysis (FR-010, spec 003).
- What happens when an age result is displayed and the person logs out? The dashboard unmounts and the held age result is discarded; re-accessing `/dashboard` requires re-authentication and shows no prior result (result is transient, not server-persisted).
- What happens when two concurrent age requests reach the backend (e.g. a race despite the frontend guard)? The backend processes each independently against the session; this is permitted (no server-side single-analysis lock — demo-first). The frontend guard prevents this in practice.
- What happens when the camera permission is denied or unavailable on age button press? The frontend shows an actionable age error surface with a message to grant camera permission and a retry option (no full page reload); no capture or backend request is initiated until permission is granted (FR-015, PRD §10). This is a frontend-only state, distinct from `invalid_image`.
- What happens to the camera stream on logout or session expiry? The dashboard unmounts and the camera stream is released (unchanged from spec 004); re-accessing `/dashboard` requires re-authentication and re-acquires the stream (no prior stream or age result is retained).
- What happens when the age range is narrow (`min == max`)? The frontend renders only the point estimate "≈NN años" (no redundant "NN–NN años" range); the backend contract still returns all three fields.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST expose `POST /api/analysis/age` accepting `multipart/form-data` with an `image` field, protected by the real session validation from spec 003 (`require_valid_session`); requests without a valid (present, non-expired, non-revoked) session MUST be rejected with `401 unauthenticated` and perform no analysis (PRD §8, FR-010, spec 003).
- **FR-002**: On a valid session and a capture containing exactly one usable face, the system MUST run the age_estimator port on the detected face and return `200 OK` with a body containing `estimatedAge` (integer), `range` (`{min, max}` integers with `min >= 0` and `min <= estimatedAge <= max`), and `disclaimer` (the exact PRD §8 string) (PRD §8, FR-013, AC-008).
- **FR-003**: The `disclaimer` MUST be the fixed string `"La edad es una estimación visual y puede contener un margen de error significativo."` on every `200` age response, and the frontend MUST render it alongside the result so the interface communicates the value is a visual estimation with a relevant error margin (PRD §6.4, §12).
- **FR-004**: The backend MUST normalize the age_estimator port output to the `{estimatedAge, range:{min,max}}` contract: if the port returns a range, `estimatedAge` is the midpoint (rounded, clamped into `[min, max]`); if the port returns only a point estimate, the backend derives a symmetric range using a configurable half-width (default 5 years, `min` clamped to 0). The half-width is the `age_range_half_width_years` field (int, default `5`, `>= 0`) on the existing pydantic `Settings` from spec 002 — no new config mechanism. The invariants `min >= 0` and `min <= estimatedAge <= max` MUST hold on every `200` response (PRD §6.4, §8).
- **FR-005**: The endpoint MUST evaluate conditions in the order: session validation → image decode/limit validation → detection (exactly one face) → age estimation → normalization → response, reusing the image limits (JPEG, ≤ 2 MB, ≤ 640px long edge) and pydantic `Settings` from spec 002 (Constitution OQ-8). Identical ordering to spec 004 mood.
- **FR-006**: Capture-quality failures MUST return `400 Bad Request` with the pinned error body `{"error": {"code": "...", "message": "..."}}` and actionable codes `no_face`, `multiple_faces`, `invalid_image`, `insufficient_quality`, with human messages indicating how to recapture; no age result MUST be produced (PRD FR-004, FR-015, specs 002/003/004 error shape).
- **FR-007**: A detector or age_estimator port/adapter error MUST return a recoverable `500 internal_error` with an actionable "try again" message and produce no age result; `401` is reserved exclusively for `unauthenticated` (session-gating) so the status-code mapping stays crisp (specs 002/003/004).
- **FR-008**: The frontend MUST capture a single still image from the camera via standard browser media APIs on age button press (no continuous streaming/frame sending), send it to `POST /api/analysis/age` with the session cookie, and show an independent age loading indicator immediately on press (PRD §6.4, §10, FR-011).
- **FR-009**: The frontend MUST disable the age button while an age analysis is in flight and ignore a second press — one capture at a time (FR-014). Because mood and age share a single camera, the mood button MUST also disable while an age analysis is in flight (shared capture mutex). On completion (success or error) both buttons MUST be re-enabled.
- **FR-010**: The frontend MUST display the most recent age result (range, point estimate, disclaimer) and keep it visible until a new age analysis is triggered or the session ends (logout/expiry); after logout the held result MUST be discarded and inaccessible without re-authentication (PRD §10, §6.4). The age result surface is independent from the mood result surface (PRD §6.4).
- **FR-011**: The frontend MUST show an independent, actionable age error surface with a retry option that does not require a full page reload on recoverable errors, separate from any mood error surface (PRD §6.4, FR-015).
- **FR-012**: The age button MUST be keyboard-accessible with a descriptive accessible name, and result/error states MUST NOT rely exclusively on color to communicate state (PRD §10).
- **FR-012a**: The frontend MUST render the age range as "min–max años" and the point estimate as "≈NN años", followed by the disclaimer. When the range is narrow (`min == max`), only the point estimate "≈NN años" MUST be rendered. The backend contract is unchanged (always returns all three fields) (PRD §6.4 — preferentemente como un rango).
- **FR-012b**: The camera stream lifecycle is unchanged from spec 004: acquired on dashboard mount (preview active) and released on dashboard unmount (logout/session expiry/navigation away). The age button captures a single still from the live preview; it does not open a separate stream per capture (PRD §6.4, §10).
- **FR-012c**: If the camera permission is denied or unavailable, the frontend MUST show an actionable age error surface with a message to grant permission and a retry option (no full page reload); no capture or backend request MUST be initiated until permission is granted (FR-015, PRD §10). This is a frontend-only state distinct from `invalid_image`.
- **FR-013**: This spec MUST enable the "Calcular edad" button that spec 004 rendered as a disabled placeholder: the "coming soon" indication MUST be removed, the button MUST become active and keyboard-accessible, and pressing it MUST trigger the age capture + `POST /api/analysis/age` flow (PRD §6.4, replaces spec 004 FR-013 placeholder).
- **FR-014**: The age analysis result MUST NOT be persisted server-side in this spec; it is transient (frontend state only). No `AnalysisRequest` audit row is written (PRD §7 optional, §19 pending; Constitution Principle I — demo-first/YAGNI). Consistent with the spec 004 mood decision.
- **FR-015**: The domain orchestration of age analysis MUST depend only on the ports (detector, age_estimator, session manager) and MUST NOT import any concrete ML model, web framework, or infrastructure adapter directly (Constitution Principle VII).
- **FR-016**: The age_estimator port MUST be wired to the mock adapter from spec 001 for this entire spec; real age models are deferred to Fase 5 and are out of scope (Constitution Principle VII; the port makes the swap a configuration change).
- **FR-017**: The age_estimator adapter MUST carry an identifiable model version so results are reproducible (PRD §11, spec 001 FR-012). The mock adapter reports the fixed string `"mock-age-estimator-v1"` (consistent with spec 001 mock naming), asserted by a unit test; real adapters in Fase 5 report their own real version strings.
- **FR-018**: An automated test suite MUST cover age unit (normalization — point→range, range→midpoint, invariants, clamping; error mapping), integration (real endpoint + mock adapters + real session validation — happy path with point estimate, range, and derived range; each capture failure; port error; unauthenticated), and contract (`200` shape, integer/range invariants, status codes `200`/`400`/`401`/`500`, pinned error body) cases, with the domain portions running without GPU, network, or real models (PRD §15, Constitution Quality Gates §5/§7).
- **FR-019**: No image, embedding, or biometric response MUST appear in application logs; observability is limited to structured JSON logs (duration, type, status of the age operation) consistent with specs 001/002/003/004 and Constitution Principle VIII (PRD §12, §13).
- **FR-020**: The mood analysis flow from spec 004 MUST NOT be re-implemented; it is reused unchanged except for the shared capture mutex (FR-009). The spec 004 mood tests MUST continue to pass (no regression).

### Key Entities *(include if feature involves data)*

- **AgeResult (transient view model)**: The result of an age analysis, returned to the frontend and held in client state. Attributes: `estimatedAge` (integer years), `range.min` and `range.max` (integer years, `min >= 0`, `min <= estimatedAge <= max`), `disclaimer` (fixed PRD §8 string). Not persisted server-side (FR-014). Derived from the detector + age_estimator ports; no new persistent entity is introduced in this spec.
- **AuthSession (from spec 003)**: The validated session gating the age endpoint. No new attributes; reused as-is via `require_valid_session`.
- **User (from spec 002)**: The authenticated person requesting the analysis. No new attributes; the session's `userId` identifies the requester for logging (not for result persistence).
- **Age Estimator Port (from spec 001)**: The hexagonal port declaring age estimation against a detected face (returns a point estimate and/or a range); the mock adapter implements it deterministically in this spec, and a real open-source model adapter will implement it in Fase 5 (Constitution Principle VII, OQ-5).
- **MoodResult (from spec 004)**: The mood result view model, unchanged. Reused to assert independence of the age and mood result surfaces (PRD §6.4).
