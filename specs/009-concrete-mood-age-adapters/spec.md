### Session 2026-09-01 (auto-resolved at specify gate)

- Q: How are the 8 AFEW emotion classes (Neutral, Happy, Sad, Surprise, Anger, Disgust, Fear, Contempt) mapped to the PRD §6.4 label set {neutral, feliz, triste, sorprendido, no concluyente}? -> A: The mood adapter performs the mapping internally before returning a `MoodResult`: Neutral→neutral, Happy→feliz, Sad→triste, Surprise→sorprendido, and Anger/Disgust/Fear/Contempt→no concluyente (the PRD label set has no categories for these four emotions, so they are reported as inconclusive rather than dropped or mislabeled). The domain `normalize_mood_label` safety net (spec 004) still maps any residual out-of-set label to "no concluyente", so the adapter mapping and the domain normalization are defense-in-depth, not redundant logic. The mapping is documented in the calibration docs (User Story 7).
- Q: Which inference runtime does each adapter use, and is the runtime pinned? -> A: The mood adapter (`EmotiEffMoodEstimator`) uses ONNX Runtime (the model file `enet_b0_8_best_afew.onnx` is an ONNX graph); the age adapter (`MiVOLOAgeEstimator`) uses PyTorch on CPU (MiVOLO is a PyTorch/timm model that loads a checkpoint, not an ONNX graph). The two adapters therefore use different runtimes — this is mandated by the model formats, not a choice. Both runtimes are CPU-only (no GPU required — Constitution Non-Goals / Quality Gate §7). `onnxruntime` was already added in spec 008; this spec adds `torch` (CPU build) and `timm` as new runtime dependencies for the age adapter, and `hsemotion-onnx` (or `emotiefflib[onnx]`) for the mood adapter.
- Q: How is the MiVOLO age checkpoint obtained and what is its license? -> A: The checkpoint is obtained via the same `ModelDownloader` from spec 008 (same `models/` cache dir, same atomic `.part`-rename download pattern, same single-attempt timeout, same load-test integrity verification). The MiVOLO code is Apache 2.0; the checkpoint license is to be verified at plan time — the working assumption is that it is distributable for research/demo use (MiVOLO checkpoints are released under the repo's Apache 2.0 or a compatible research-use license). If plan-time verification finds an incompatible license, the adapter is swapped behind the `AgeEstimator` port (Constitution Principle VII) without a spec change. The checkpoint filename and download URL are pinned in the adapter constants (plan-time detail).
- Q: Does the mood adapter return a confidence value, and how is it derived? -> A: Yes. The EmotiEff/HSEmotion model outputs a softmax probability distribution over the 8 AFEW classes. The adapter takes the argmax class (→ mapped label) and its probability as the confidence (a float in [0, 1]). The domain `MoodService` clamps the confidence to [0, 1] (spec 004) as a safety net. When the top-1 probability is below a configurable mood confidence threshold, the adapter returns "no concluyente" with the low confidence value, so low-certainty predictions are surfaced as inconclusive rather than as a confident wrong label.
- Q: Does the age adapter return a point estimate, a range, or both? -> A: MiVOLO's face-only age model returns a point age estimate (an integer or float that the adapter rounds to an integer). The adapter returns an `AgeResult` with `estimated_age` set to the rounded point estimate and `range=None` (point-only). The domain `AgeService.normalize_age_result` (spec 005) then derives a symmetric range around the estimate using the existing `age_range_half_width_years` setting (default 5), guaranteeing the response contract invariants (`min >= 0`, `min <= estimatedAge <= max`). This reuses the exact normalization path already exercised by the mock age estimator's point-only mode (spec 005), so no domain change is introduced.
- Q: Do both adapters use the shared face-crop pipeline from spec 008 for face alignment before inference? -> A: Yes. Both adapters decode the incoming image bytes, run an internal YuNet detection (reusing the YuNet model already cached by spec 008's `YuNetDetector`/`SFaceEmbedder`) to locate the face box + landmarks, then pass the detected face through the shared `face_crop` alignment pipeline before running model inference. This mirrors the `SFaceEmbedder` pattern (spec 008, research R-5: double-detection is acceptable because the port signature receives raw image bytes, not a pre-cropped face). The aligned crop improves mood/age inference quality; without it the model receives an unaligned region and accuracy degrades (a quality edge case, not a crash).
- Q: What new runtime dependencies are added, and are they isolated from the domain/mock path? -> A: `torch` (CPU build — `torch` installed without CUDA, or `torch==<version>+cpu`), `timm` (PyTorch image models, required by MiVOLO), and `hsemotion-onnx` or `emotiefflib[onnx]` (the EmotiEff/HSEmotion ONNX inference wrapper). `opencv-python-headless` and `onnxruntime` were already added in spec 008 and are reused. All new dependencies are imported only by the concrete mood/age adapters, never by the domain layer or the mock wiring path (Constitution Principle VII). The domain purity test (spec 001) continues to assert no `torch`/`timm`/`hsemotion`/`onnxruntime`/`cv2` import in the domain.
- Q: What happens to the detector and embedder in production mode after this spec? -> A: Unchanged. `wire_production_adapters()` already wires `YuNetDetector` + `SFaceEmbedder` (spec 008). This spec only substitutes the mood and age estimators from mock to concrete; the detector, embedder, persistence adapters, image storage, and all services are unchanged. After this spec, production mode wires real adapters for all four ML ports (detector, embedder, mood, age) + real DB persistence — Fase 5 is complete.
- Q: Is the mood confidence threshold a new setting, and where does it live? -> A: Yes — a new `mood_confidence_threshold` field (float, default 0.5, clamped to [0, 1]) is added to the existing pydantic `Settings` from spec 002, following the same pattern as `quality_threshold` and `age_range_half_width_years`. When the mood model's top-1 softmax probability is below this threshold, the adapter returns "no concluyente". The threshold is configurable via the environment and documented in the calibration docs (User Story 7). The mock mood estimator is unaffected (it returns a fixed confidence above the default threshold).

### User Story 1 - Real Mood Estimation via EmotiEff/HSEmotion in Production Mode (Priority: P1)

When the application is started in production mode (`APP_MODE=production`) with the concrete ML adapters wired, the dashboard's "Detectar estado de ánimo" flow performs **real mood estimation** using the EmotiEff/HSEmotion open-source emotion recognition model (ONNX Runtime). The mood adapter (`EmotiEffMoodEstimator`) implements the existing `MoodEstimator` port and returns a `MoodResult` containing a mood label from the PRD §6.4 set `{neutral, feliz, triste, sorprendido, no concluyente}`, a confidence value in [0, 1], and an identifiable `model_version`. The adapter maps the model's 8 AFEW emotion classes to the PRD label set; when the top-1 prediction probability is below the configurable mood confidence threshold, the adapter returns "no concluyente" so low-certainty predictions are surfaced as inconclusive. Given a test image containing exactly one face, the real mood estimator returns a valid label from the PRD set and a confidence in [0, 1]. The domain layer never imports ONNX Runtime, HSEmotion, or the model directly (Constitution Principle VII). This resolves Constitution Open Question OQ-5 (mood model portion).

**Why this priority**: Real mood estimation is the first half of the spec's core deliverable and the reason it exists. Without a concrete mood estimator, the production app returns a deterministic mock label (`neutral`, confidence `0.74`) regardless of the actual face, which defeats the purpose of the dashboard's mood analysis (PRD §6.4, AC-007). It delivers PRD §18 Fase 5 ("integrar modelo de estado de ánimo"), PRD §11 (model version + domain isolation), PRD §6.4 (Resultado de estado de ánimo — label + optional confidence + "no concluyente" fallback), and Constitution Principle III (open-source ML). Every subsequent story depends on this adapter existing and conforming to the port.

**Independent Test**: Start the app with `APP_MODE=production` and the EmotiEff/HSEmotion model present in the models cache. Feed a test image containing exactly one face through the mood estimator; assert the returned `MoodResult.label` is a member of `{neutral, feliz, triste, sorprendido, no concluyente}`, `confidence` is a float in [0, 1], and `model_version` is a non-empty string distinct from the mock version. Feed a face-less image through the detector → the domain `MoodService` raises `NoFace` (the adapter is never called). Assert the domain layer source has no `onnxruntime` / `hsemotion` / `emotieff` import. Delivers a verifiable real mood estimator behind the port.

**Acceptance Scenarios**:

1. **Given** the app is started with `APP_MODE=production` and the EmotiEff/HSEmotion model is available, **When** an image containing exactly one face is analyzed for mood, **Then** `EmotiEffMoodEstimator.estimate_mood()` returns a `MoodResult` with `label` in `{neutral, feliz, triste, sorprendido, no concluyente}`, `confidence` in [0, 1], and a non-empty `model_version` (PRD §6.4, FR-012).
2. **Given** the model's top-1 softmax probability is below the configured mood confidence threshold, **When** the mood is estimated, **Then** the returned `label` is "no concluyente" (low-certainty predictions are surfaced as inconclusive, not as a confident wrong label).
3. **Given** the 8 AFEW emotion classes, **When** the adapter maps them to the PRD label set, **Then** Neutral→neutral, Happy→feliz, Sad→triste, Surprise→sorprendido, and Anger/Disgust/Fear/Contempt→no concluyente.
4. **Given** the domain layer, **When** its imports are inspected, **Then** it has no direct dependency on ONNX Runtime, HSEmotion, EmotiEffLib, or any concrete model file (Constitution Principle VII, PRD §11).
5. **Given** `EmotiEffMoodEstimator`, **When** its `model_version` is inspected, **Then** it exposes an identifiable, fixed version string (e.g. `emotieff-enet-b0-afew-v1`) distinct from the mock version (`mock-mood-v1`) so results are reproducible (PRD §11 — "los modelos deben tener una versión identificable").

### User Story 3 - Shared Face-Crop Reuse for Mood & Age Alignment (Priority: P2)

Both concrete mood and age adapters use the shared face-crop and alignment pipeline (`face_crop`) from spec 008 to align the detected face before running model inference. Each adapter decodes the incoming image bytes, runs an internal YuNet detection (reusing the YuNet model already cached by spec 008) to locate the face box + landmarks, then passes the detected face through the shared `face_crop` alignment pipeline. This mirrors the `SFaceEmbedder` pattern (spec 008): double-detection is acceptable because the `MoodEstimator.estimate_mood` and `AgeEstimator.estimate_age` port signatures receive raw image bytes, not a pre-cropped face. The aligned crop improves mood/age inference quality. The `face_crop` utility is an internal adapter-layer function — not a domain port — and the domain layer does not import it directly.

**Why this priority**: The crop/align pipeline is the glue between detection and mood/age inference: without it, the mood and age models receive a raw, unaligned region and inference quality degrades, weakening the label/age accuracy that User Stories 1 and 2 depend on. It is independently testable by feeding a known image + box + landmarks into the face-crop pipeline via each adapter and asserting the model receives a fixed-size aligned crop. It is P2 because it supports the P1 adapters rather than standing alone as user-visible value. It reuses the existing `face_crop` from spec 008 — no new alignment code is introduced.

**Independent Test**: Feed a test image with a known single face into `EmotiEffMoodEstimator.estimate_mood()` and `MiVOLOAgeEstimator.estimate_age()`; assert both produce a valid result (mood label + confidence / age estimate), confirming the internal detect → align → infer path works end-to-end through the shared `face_crop`. Feed a degenerate image with no face; assert both adapters raise a clear error (no face detected for alignment). Delivers a verifiable alignment reuse path feeding both models.

**Acceptance Scenarios**:

1. **Given** a source image with exactly one face, **When** the mood or age adapter runs, **Then** it internally detects the face, passes it through the shared `face_crop` alignment pipeline from spec 008, and runs model inference on the aligned crop.
2. **Given** the mood and age adapters, **When** their alignment path is inspected, **Then** both reuse the same `face_crop` utility from spec 008 (no new alignment code is introduced).
3. **Given** a source image with no face, **When** the mood or age adapter runs, **Then** it raises a clear error indicating no face was detected for alignment (the model is not invoked on an empty/invalid crop).
4. **Given** the domain layer, **When** its imports are inspected, **Then** it does not import the `face_crop` utility directly (the pipeline lives in the adapters layer, invoked by the adapter composition — Constitution Principle VII).

### User Story 4 - Model Download Reuse for Mood & Age Models (Priority: P2)

The concrete mood and age adapters obtain their model files (`enet_b0_8_best_afew.onnx` for mood, the MiVOLO face-only age checkpoint for age) from the same local cache directory (`models/`) at the repo root used by spec 008. The `ModelDownloader` utility from spec 008 fetches each model from its source URL on first use if the file is absent (lazy download), and serves it from the cache on subsequent uses. The same atomic `.part`-rename download pattern, single-attempt timeout (default 30s connect / 120s read), and load-test integrity verification apply. The `models/` directory is already bind-mounted into the backend container via Docker Compose (spec 008). Models may alternatively be pre-downloaded for air-gapped/offline demos. The model cache path is configurable (already added in spec 008).

**Why this priority**: Without a reliable, reproducible way to obtain and cache the mood and age model files, the concrete adapters cannot load and the production app fails to start. It reuses the infrastructure from spec 008 (no new downloader, no new cache dir, no new compose volume) — only two new model files are added to the existing cache. It is independently testable by starting with an empty cache, triggering adapter construction, and asserting each model file is downloaded once and reused. It is P2 because it is the enabling infrastructure for the P1 adapters.

**Independent Test**: Start with an empty `models/` cache and `APP_MODE=production`; trigger mood/age adapter construction; assert each model file is downloaded once into `models/` and that a second construction reuses the cached file (no re-download). Assert the existing spec 008 model files (YuNet, SFace) are also present and unaffected. Delivers a verifiable, cached model supply reusing the spec 008 infrastructure.

**Acceptance Scenarios**:

1. **Given** the `models/` cache is empty and network is available, **When** a concrete mood or age adapter is first constructed, **Then** `ModelDownloader` fetches the required model file from its source URL into `models/` and the adapter loads it.
2. **Given** the model file already exists in `models/`, **When** the adapter is constructed, **Then** the cached file is reused and no network fetch occurs.
3. **Given** the docker-compose production stack, **When** the backend container starts, **Then** the `models/` directory is already bind-mounted into the container (spec 008) and the mood/age model files are accessible at the same path (Constitution Principle IV).
4. **Given** an air-gapped environment with the mood/age model files pre-placed in `models/`, **When** the app starts, **Then** the adapters load from the cache without any network access (pre-download supported).
5. **Given** a model download fails (network error, corrupt file), **When** the adapter is constructed, **Then** it fails fast with a clear, actionable error indicating which model could not be obtained, before serving traffic (reusing the spec 008 `ModelUnavailableError` / `ModelCorruptError` pattern).

### User Story 6 - Real-Model Integration Tests (Priority: P3)

An automated integration test suite exercises the concrete mood and age adapters with real model files. The tests verify: (a) the mood estimator returns a valid label from the PRD §6.4 set `{neutral, feliz, triste, sorprendido, no concluyente}` and a confidence in [0, 1]; (b) the age estimator returns a non-negative integer `estimated_age` with `range=None` (point-only), and the domain-normalized result satisfies the invariants (`min >= 0`, `min <= estimatedAge <= max`); (c) both adapters handle a no-face image by raising a clear error (the detector finds zero faces before the estimator is invoked); (d) both adapters handle a multiple-faces image via the detector (the domain rejects multi-face per specs 004/005). The tests are skipped when the model files are absent (via the `pytest.mark.requires_models` marker / autouse fixture from spec 008) or when `APP_MODE != production`, so CI without models still runs the rest of the suite green. The tests use consented test fixture images only (PRD §12).

**Why this priority**: Tests are the safety net that confirms the concrete mood/age adapters actually work against real models and that the label mapping, confidence range, and age invariants hold — the core correctness claims of the spec. It delivers Constitution Quality Gates §6/§7 (integration tests for real adapters; ML-adapter integration tests may be skipped in CI with a documented flag). It is independently testable by running the suite with models present (pass) and absent (skipped, suite still green). It is P3 because it validates the P1/P2 deliverables rather than delivering standalone user value.

**Independent Test**: Run the real-model integration suite with all models present; assert all mood/age assertions pass (valid label, confidence in [0,1], non-negative age, range invariants). Remove the mood/age models from the cache and re-run; assert the real-model tests are skipped and the rest of the suite remains green. Delivers a green, reproducible real-model test layer that is gracefully skippable.

**Acceptance Scenarios**:

1. **Given** the model files are present and `APP_MODE=production`, **When** the real-model mood tests run, **Then** the mood estimator returns a label in `{neutral, feliz, triste, sorprendido, no concluyente}` and a confidence in [0, 1] for a single-face fixture.
2. **Given** the model files are present and `APP_MODE=production`, **When** the real-model age tests run, **Then** the age estimator returns a non-negative integer `estimated_age` with `range=None`, and the domain-normalized result satisfies `min >= 0` and `min <= estimatedAge <= max`.
3. **Given** a no-face fixture, **When** the mood or age adapter path runs, **Then** the detector returns `face_count == 0` and the domain raises `NoFace` (the estimator is not invoked).
4. **Given** a multiple-faces fixture, **When** the mood or age adapter path runs, **Then** the detector returns `face_count > 1` and the domain raises `MultipleFaces` (the estimator is not invoked).
5. **Given** the model files are absent, **When** the test suite runs, **Then** the real-model mood/age tests are skipped (via `requires_models` / `APP_MODE` guard) and the remainder of the suite passes green (Constitution Quality Gate §7).

### Edge Cases

- What happens when `APP_MODE=mock`? The app wires mock adapters, requires no model files and no ONNX Runtime/PyTorch runtime, and behaves identically to specs 001-008 (backward compatible).
- What happens when `APP_MODE=production` but the mood or age model files are absent and network is unavailable? The concrete adapter construction fails fast with a clear, actionable error indicating which model could not be obtained, before serving traffic (reusing the spec 008 `ModelUnavailableError` pattern).
- What happens when a mood or age model file is present but corrupt? The adapter fails fast at load time with a clear error (model-load failure via the spec 008 load-test pattern), mapped to a recoverable `500 internal_error` at the HTTP boundary; it does not silently produce garbage mood/age results.
- What happens when the detector finds zero faces in a mood/age analysis? The existing domain behavior from specs 004/005 applies unchanged (the domain `MoodService`/`AgeService` raises `NoFace` → `400 no_face`); the real estimator is never invoked.
- What happens when the detector finds multiple faces in a mood/age analysis? The existing domain behavior applies (the domain raises `MultipleFaces` → `400 multiple_faces`); the real estimator is never invoked.
- What happens when the mood model's top-1 probability is below the `mood_confidence_threshold`? The adapter returns "no concluyente" with the low confidence value, so low-certainty predictions are surfaced as inconclusive rather than as a confident wrong label.
- What happens when the mood model returns an AFEW class that maps to "no concluyente" (Anger, Disgust, Fear, Contempt)? The adapter maps it to "no concluyente" internally; the domain normalizer is a safety net that also maps any residual out-of-set label to "no concluyente".
- What happens when the age model returns a point estimate near 0 (e.g. a baby)? The domain `normalize_age_result` clamps `min` to 0 (age cannot be negative) and derives the symmetric range; the response satisfies `min >= 0` and `min <= estimatedAge <= max`.
- What happens when the age model returns a very large point estimate (e.g. 100+)? The domain normalization handles it without special casing; the range is derived symmetrically. No upper bound is enforced (the model's output is trusted within its documented error margin).
- What happens when the mood/age adapters receive an unaligned/raw crop (alignment skipped)? The models still produce a result, but inference accuracy degrades; the shared face-crop pipeline (User Story 3) is the supported path. This is a quality edge case, not a crash.
- What happens when the model download is interrupted mid-fetch? The spec 008 atomic `.part`-rename pattern applies: a partial file is never left as a valid cache entry; the next construction finds no valid cached file and re-downloads.
- What happens when `models/` is read-only (cannot write the cache)? The adapter fails fast with a clear error indicating the cache directory is not writable; pre-placing the model files (pre-download) is the supported workaround for read-only environments (spec 008 pattern).
- What happens when the real-model integration tests run without Docker or without models? They are skipped via the `requires_models` / `APP_MODE` guard; the rest of the suite remains green (Constitution Quality Gate §7).
- What happens if a developer changes a mock adapter in this spec? That is out of scope (scope boundary); mock adapters are retained verbatim.
- What happens if a developer changes a domain port, entity, or result type in this spec? That is out of scope (scope boundary); the spec is additive — new concrete adapters implement existing ports. No port, entity, or result type is added or altered.
- What happens if a developer adds a new HTTP endpoint or frontend change in this spec? That is out of scope (scope boundary); the existing PRD §8 contracts are served identically; the frontend is unaware of the adapter substitution.
- What happens to the detector and embedder in production mode? They remain the concrete `YuNetDetector` + `SFaceEmbedder` from spec 008 (unchanged by this spec). Only the mood and age estimators are substituted.
- What happens to logs? No image, mood label, age estimate, or biometric response is logged; observability is limited to structured JSON logs (adapter loaded, model version, operation duration/status) consistent with specs 001-008 and Constitution Principle VIII (PRD §12/§13).
- What happens if the MiVOLO checkpoint license is found incompatible at plan time? The adapter is swapped behind the `AgeEstimator` port (Constitution Principle VII) without a spec change; the port abstraction is the constitutional safeguard.
