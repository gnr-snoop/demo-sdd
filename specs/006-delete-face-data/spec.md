This spec implements the DELETE /api/users/{userId}/face-data endpoint and the backend operation to eliminate a profile and its facial template, building on specs 001-004. It covers PRD §8 (DELETE /api/users/{userId}/face-data — Elimina la plantilla facial y los datos asociados al onboarding. This is the 'right to be forgotten' demo operation. IN: real DELETE endpoint logic, unit + integration + contract tests, frontend logout-after-deletion handling. ## Clarifications

### Session 2026-08-31 (auto-resolved at specify gate)

- Q: Hard delete the `User` row or soft-delete (mark `status = disabled`)? -> A: Hard delete. The `User`, `FaceTemplate`, and all `AuthSession` rows for the user are physically removed from PostgreSQL. Constitution Principle I (demo-first) and YAGNI favor the simplest thing that could possibly work: a hard delete makes "the user is gone" literally true and makes the "right to be forgotten" demo narrative unambiguous (no zombie disabled rows to explain). Soft-delete/retention policies are explicitly out of scope (Principle VIII — no traceability guarantee; no audit/retention requirement). With hard delete, post-deletion login fails at the identifier-lookup step (no `User`) and returns the generic `401 auth_failed` from spec 003 — the person is fully forgotten by the system.
- Q: What is the authorization model for the endpoint? -> A: The caller must be the authenticated user themselves: the session's `userId` MUST equal the path `userId`. There is no admin panel (PRD §4 non-goal) and no admin role/token (Principle VIII — no security guarantee). A valid session is required first (real `require_valid_session` from spec 003); then the path `userId` is compared to the session's `userId`. A mismatch returns `403 forbidden` — the caller is authenticated but trying to delete someone else's data, which is a distinct, intentionally-revealing authorization failure (unlike login's non-revealing `auth_failed`, here the caller is already authenticated and the demo narrative is "you can only delete your own data"). This is demo-grade authorization (Principle VIII); it is not a security guarantee.
- Q: In what order does the endpoint evaluate conditions? -> A: (1) path-parameter validation (`userId` is a valid UUID v4) → `422` validation error if malformed (FastAPI path validation, before the handler); (2) session validation via `require_valid_session` → `401 unauthenticated` if no valid session; (3) authorization check (`session.userId == path userId`) → `403 forbidden` if mismatch; (4) load the `User` for the path `userId` → `404 not_found` if the user does not exist (defensive guard against out-of-band deletion; with a valid matching session this is an edge case); (5) execute the deletion operation (DB transaction + best-effort filesystem cleanup); (6) clear the session cookie on the response (the current session is among those revoked); (7) return `200 OK` with `{userId, status: "deleted"}`. A DB or filesystem port error at step 5 returns a recoverable `500 internal_error` (actionable: "try again") and, for DB errors, leaves no partial deletion (transaction rollback).
- Q: How is the deletion transactional, and what happens if the filesystem deletion fails? -> A: The database deletions (`FaceTemplate` rows, `AuthSession` rows, `User` row) execute inside a single PostgreSQL transaction: dependents first (`FaceTemplate`, `AuthSession`), then the parent `User`, then commit. If the transaction fails, it rolls back and the endpoint returns `500 internal_error` with no partial DB state. After a successful DB commit, the filesystem cleanup (`usuarios/<user-id>/` folder and `pictures.jpg`) is best-effort: if the folder does not exist or its deletion fails, the endpoint STILL returns `200` success and logs a structured warning. Rationale: the DB is the source of truth for login (no `FaceTemplate` → no login); an orphaned image folder is a minor demo inconsistency, not a functional failure, and adding a two-phase commit across DB + filesystem would violate Principle I (demo-first). The warning is observable without logging any image/embedding content (Principle VIII).
- Q: Is there a frontend UI trigger for deletion, or is the endpoint backend-only? -> A: There is a frontend trigger. The `/dashboard` gains a keyboard-accessible "Eliminar mis datos" button that, on press, shows a simple confirmation dialog ("Esta acción eliminará tu perfil y plantilla facial de forma permanente. ¿Continuar?"). On confirm, the frontend calls `DELETE /api/users/{userId}/face-data` with the session cookie and the session's `userId` as the path parameter. On `200` success, the frontend clears all session state, releases the camera stream, and navigates to `/` (the welcome page). This delivers the "right to be forgotten" as a user-facing demo operation (FR-017 — "durante la demo"), not just a backend primitive. The confirmation step prevents accidental destructive deletion; it is a lightweight native confirm, not a full settings page (Principle I — demo-first).
- Q: What does the response do with the session cookie? -> A: The backend clears (expires) the session cookie on the `200` deletion response, because the current `AuthSession` is among the rows deleted in step 5. The frontend also clears its in-memory session state. This is consistent with spec 003's logout cookie-clearing behavior and ensures the client does not hold a stale cookie referencing a deleted session.
- Q: Where is the person redirected after deleting their own data? -> A: To `/` (the welcome page), per the feature description. This is distinct from logout (which redirects to `/login`): after deletion there is no profile to log in with, so sending the person to the welcome/onboarding entry point is the coherent demo narrative. The frontend releases the camera stream and discards any held analysis results (mood/age) on this transition.
- Q: Is the deletion idempotent? -> A: No special idempotence is implemented. A valid session guarantees the `User` exists, so the first call succeeds and destroys the session; a second call with the now-deleted session receives `401 unauthenticated` (the session is gone). This is the natural, demo-first behavior — no idempotent `200`-on-already-deleted semantics are added (YAGNI).
- Q: What happens if the `usuarios/<user-id>/` folder does not exist but the DB rows do (or vice versa)? -> A: The DB transaction is the authoritative operation. If the folder is already absent at deletion time, the filesystem cleanup is a no-op and the endpoint still returns `200` (best-effort). If the DB rows are absent but a folder exists (out-of-band partial state), the endpoint reaches step 4 (`User` not found) and returns `404 not_found` without touching the filesystem — the authorized caller's own user row is gone, which means their session would already be invalid, so this path is only reachable via out-of-band tampering and is a documented demo edge case (Principle VIII).
- Q: Are real ML models involved in deletion? -> A: No. Deletion is a pure data/infrastructure operation: it touches PostgreSQL (via repository/session-manager ports) and the local filesystem (via the image-storage port). No detector, embedder, mood, or age port is invoked. The mock vs real model distinction is irrelevant to this spec; Fase 5 model work is out of scope.

Error responses reuse the spec-002-pinned `{"error": {"code": "...", "message": "..."}}` shape with codes `unauthenticated` (401), `forbidden` (403), `not_found` (404), `internal_error` (500), plus FastAPI `422` for malformed UUID. The DB deletion is a single transaction (dependents first, then `User`); filesystem cleanup is best-effort after commit. Hard delete (no soft-delete/retention). Authorization = session `userId` matches path `userId`. This is pinned and flows into plan, contracts, and contract-test assertions.

### User Story 1 - Successful Face Data Deletion (Happy Path) (Priority: P1)

A person with a valid session is on `/dashboard`. They press the keyboard-accessible "Eliminar mis datos" button and confirm the deletion dialog. The frontend sends `DELETE /api/users/{userId}/face-data` with the session cookie and the session's `userId` as the path parameter. The backend validates the session (spec 003 `require_valid_session`), confirms the path `userId` matches the session's `userId`, loads the `User`, and executes the deletion operation inside a single PostgreSQL transaction: it deletes the `FaceTemplate` row(s) for the user, deletes all `AuthSession` rows for the user (revoking every session including the current one), deletes the `User` row (hard delete), and commits. After the commit, it deletes the filesystem folder `usuarios/<user-id>/` and its `pictures.jpg` (best-effort). It clears the session cookie on the response and returns `200 OK` with `{userId, status: "deleted"}` per PRD §8. The frontend clears all session state, releases the camera stream, discards any held analysis results, and navigates to `/`.

**Why this priority**: This is the core "right to be forgotten" narrative and the primary deliverable of the Fase 6 hardening portion. It delivers PRD §8 (DELETE endpoint), FR-017 (eliminar datos faciales), and Constitution Principles V (filesystem deletion) and VI (DB deletion) end-to-end. Without a working deletion operation the demo has no way to remove a profile and its biometric template, which is a PRD §12 privacy requirement ("permitir eliminar la plantilla facial").

**Independent Test**: Perform a successful onboarding + login (specs 002/003) so that a `User`, `FaceTemplate`, `AuthSession`, and `usuarios/<user-id>/pictures.jpg` all exist. Call `DELETE /api/users/{userId}/face-data` with the session cookie and the matching `userId`; assert a `200` response with `userId` (echoed) and `status == "deleted"`, a cleared cookie, and that the `User`, `FaceTemplate`, and `AuthSession` rows are gone from PostgreSQL and the `usuarios/<user-id>/` folder is gone from the filesystem. Delivers a complete, demonstrable face-data deletion.

**Acceptance Scenarios**:

1. **Given** the person has a valid session and is on `/dashboard`, **When** they press "Eliminar mis datos" and confirm the dialog, **Then** the frontend sends `DELETE /api/users/{userId}/face-data` with the session cookie and the session's `userId` as the path parameter (PRD §8, FR-017).
2. **Given** a valid session and a matching path `userId`, **When** the backend processes the deletion, **Then** it deletes the `FaceTemplate` row(s), all `AuthSession` rows, and the `User` row in a single PostgreSQL transaction, and commits (Constitution Principle VI).

### User Story 2 - Authorization & Session Gating on Deletion (Priority: P2)

The `DELETE /api/users/{userId}/face-data` endpoint is protected by the real session validation from spec 003 and an authorization check: a request without a valid (present, non-expired, non-revoked) session is rejected with `401 unauthenticated` and performs no deletion; a request with a valid session whose `userId` does not match the path `userId` is rejected with `403 forbidden` and performs no deletion. A malformed path `userId` (not a UUID v4) is rejected with `422` validation error before the handler runs. These checks ensure the only way to delete face data is for the authenticated person to delete their own data — there is no admin path (PRD §4 non-goal).

**Why this priority**: Authorization is what makes deletion safe-ish in the demo: only the owner can delete their own biometric data. It delivers the "Requiere autorización apropiada" clause of PRD §8 and Constitution Principle VIII (demo-grade authorization — no security guarantee, but the obvious abuse is blocked). It is independently testable by calling the endpoint with no session, a mismatched `userId`, and a malformed `userId`, and asserting each rejection and that no data is removed.

**Independent Test**: Seed two users (A and B) with valid sessions. (a) Call `DELETE /api/users/{A}/face-data` with no cookie → assert `401 unauthenticated` and no rows removed. (b) Call it with A's cookie but B's `userId` in the path → assert `403 forbidden` and no rows removed for A or B. (c) Call it with A's cookie and a malformed `userId` (`not-a-uuid`) → assert `422` and no rows removed. (d) Call it with an expired/revoked session → assert `401 unauthenticated`. Delivers correct, demo-grade authorization on deletion.

**Acceptance Scenarios**:

1. **Given** no valid session, **When** `DELETE /api/users/{userId}/face-data` is called, **Then** it returns `401 unauthenticated` and performs no deletion (FR-010, spec 003).
2. **Given** an expired or revoked session, **When** the endpoint is called, **Then** it returns `401 unauthenticated` and performs no deletion.
3. **Given** a valid session for user A, **When** the endpoint is called with user B's `userId` in the path, **Then** it returns `403 forbidden` and performs no deletion for either user (PRD §8 — autorización apropiada).
4. **Given** a valid session, **When** the endpoint is called with a malformed `userId` (not a UUID v4), **Then** it returns `422` validation error and performs no deletion.
5. **Given** a `401`/`403`/`422` rejection, **When** the database and filesystem are inspected, **Then** no `User`, `FaceTemplate`, `AuthSession`, or `usuarios/<user-id>/` folder has been removed.

### User Story 3 - Post-Deletion Invalidation & "Right to Be Forgotten" Verification (Priority: P3)

After a successful deletion, the person is fully forgotten by the system: (1) the old session cookie is invalid — `GET /api/auth/me` with the old cookie returns `401 unauthenticated`; (2) the person cannot log in — `POST /api/auth/face-login` with the old identifier returns `401 auth_failed` (no `User`/`FaceTemplate` found, indistinguishable from a never-enrolled identifier per spec 003's non-revealing contract); (3) the filesystem folder `usuarios/<user-id>/` and its `pictures.jpg` no longer exist; (4) no `User`, `FaceTemplate`, or `AuthSession` rows for that `userId` remain in PostgreSQL. This is the verifiable "right to be forgotten" outcome.

**Why this priority**: This is the proof that deletion actually achieved its purpose — the biometric data is gone and the person cannot be authenticated. It validates Constitution Principles V (filesystem) and VI (DB) and the PRD §12 privacy requirement. It is independently testable by performing a deletion and then attempting login and session validation with the old credentials/cookie.

**Independent Test**: Perform onboarding + login for identifier `demo@example.com`, then a successful deletion. (a) Call `GET /api/auth/me` with the old cookie → assert `401 unauthenticated`. (b) Call `POST /api/auth/face-login` with `demo@example.com` and a matching fixture image → assert `401 auth_failed` (no profile). (c) Inspect PostgreSQL → assert no `User`, `FaceTemplate`, or `AuthSession` rows for that `userId`. (d) Inspect the filesystem → assert `usuarios/<user-id>/` does not exist. Delivers a verified "right to be forgotten".

**Acceptance Scenarios**:

1. **Given** the deletion succeeded, **When** `GET /api/auth/me` is called with the old session cookie, **Then** it returns `401 unauthenticated` (the session was deleted).
2. **Given** the deletion succeeded, **When** `POST /api/auth/face-login` is called with the old identifier and any image, **Then** it returns `401 auth_failed` indistinguishable from a never-enrolled identifier (spec 003 FR-008).
3. **Given** the deletion succeeded, **When** PostgreSQL is inspected, **Then** no `User`, `FaceTemplate`, or `AuthSession` rows for that `userId` exist (Constitution Principle VI).
4. **Given** the deletion succeeded, **When** the filesystem is inspected, **Then** the `usuarios/<user-id>/` folder and its `pictures.jpg` do not exist (Constitution Principle V).
5. **Given** the deletion succeeded, **When** the person attempts to navigate to `/dashboard`, **Then** the frontend `ProtectedRoute` redirects them to `/login` (no valid session).

### Edge Cases

- What happens when the path `userId` is not a valid UUID v4? The backend returns `422` validation error (FastAPI path validation) before the handler runs and performs no deletion.
- What happens when the authenticated user's session `userId` does not match the path `userId`? The backend returns `403 forbidden` and performs no deletion; the caller is authenticated but not the owner (PRD §8 — autorización apropiada).
- What happens when the `User` for the path `userId` does not exist (out-of-band deletion)? The backend returns `404 not_found` and performs no deletion. With a valid matching session this is an edge case (the session guarantees the user exists); it is reachable only if the user row was removed out of band while the session remained.
- What happens when the filesystem folder `usuarios/<user-id>/` does not exist at deletion time? The filesystem cleanup is a no-op (best-effort); the endpoint still returns `200` after the DB commit. The folder's absence is not a failure.
- What happens when the filesystem deletion fails (e.g. permission error) after the DB transaction commits? The endpoint still returns `200` success and logs a structured warning; the DB is the source of truth for login, so the user is effectively forgotten. An orphaned image folder is a minor demo inconsistency, not a functional failure (Constitution Principle I — demo-first; no two-phase commit).
- What happens when the DB transaction fails mid-deletion? The transaction rolls back, no partial DB state is left (no `User`/`FaceTemplate`/`AuthSession` removed), the filesystem is not touched, and the endpoint returns `500 internal_error` with a recoverable "try again" message.
- What happens when the person calls deletion twice rapidly? The first call succeeds and destroys the session; the second call (with the now-deleted session) receives `401 unauthenticated`. The frontend button is disabled during the in-flight first call, preventing the double submission in practice.
- What happens when the user has multiple concurrent sessions (spec 003 — no single-session constraint)? All `AuthSession` rows for the user are deleted in the transaction; every session is invalidated, not just the current one.
- What happens when the person cancels the confirmation dialog? No request is made; no deletion occurs; the dashboard remains unchanged.
- What happens when the session expires or is revoked while the deletion request is in flight? The in-flight request receives `401 unauthenticated`; the frontend transitions to the unauthenticated state (redirect to `/login`) and discards any pending deletion result.
- What happens to held mood/age analysis results after deletion? They are discarded by the frontend on the transition to `/`; they were transient (spec 004) and are no longer accessible without re-onboarding.
- What happens when the person navigates to `/dashboard` after deletion? `ProtectedRoute` redirects to `/login` (no valid session); attempting to log in with the old identifier returns `401 auth_failed` (no profile).
- What happens when the `userId` path parameter is valid but the session belongs to a different user who was already deleted? The session is invalid (its `AuthSession` was deleted with the user), so `require_valid_session` returns `401 unauthenticated` before the authorization check.
- What happens if a concurrent request deletes the user between the session check and the deletion operation? The deletion operation's `User` load returns not-found and the endpoint returns `404 not_found`; no partial deletion occurs. This is a rare race in the demo and is handled defensively.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST expose `DELETE /api/users/{userId}/face-data` accepting a `userId` UUID v4 path parameter and a valid session cookie; requests without a valid (present, non-expired, non-revoked) session MUST be rejected with `401 unauthenticated` and perform no deletion (PRD §8, FR-010, spec 003).
- **FR-002**: The endpoint MUST authorize the caller by comparing the session's `userId` to the path `userId`; a mismatch MUST return `403 forbidden` and perform no deletion. There MUST be no admin/impersonation path (PRD §4 non-goal, Constitution Principle VIII — demo-grade authorization).
- **FR-003**: A malformed `userId` (not a UUID v4) MUST be rejected with `422` validation error before the handler executes, and perform no deletion (spec 001 contract).
- **FR-004**: On a valid session and matching `userId`, the system MUST delete, in a single PostgreSQL transaction: the `FaceTemplate` row(s) for the user, all `AuthSession` rows for the user, and the `User` row (hard delete — dependents first, then the parent), and commit. If the transaction fails, it MUST roll back and return `500 internal_error` with no partial DB state (Constitution Principle VI, Principle I — hard delete for demo simplicity).
- **FR-005**: After a successful DB commit, the system MUST delete the filesystem folder `usuarios/<user-id>/` and its `pictures.jpg` on a best-effort basis; if the folder is absent or its deletion fails, the endpoint MUST still return `200` success and log a structured warning. The filesystem cleanup MUST NOT cause the endpoint to fail after a successful DB commit (Constitution Principle V, Principle I — no two-phase commit).
- **FR-006**: On successful deletion, the system MUST return `200 OK` with body `{"userId": "<echoed UUID v4>", "status": "deleted"}` and clear the session cookie on the response (PRD §8).
- **FR-007**: If the `User` for the path `userId` does not exist at deletion time, the system MUST return `404 not_found` and perform no deletion (defensive guard against out-of-band deletion).
- **FR-008**: The endpoint MUST evaluate conditions in the order: path-parameter validation (`422`) → session validation (`401 unauthenticated`) → authorization check (`403 forbidden`) → user lookup (`404 not_found`) → deletion operation → cookie clear → `200` response. A DB/filesystem port error during the deletion operation MUST return `500 internal_error` with an actionable "try again" message (specs 002/003 error mapping).
- **FR-009**: After a successful deletion, the old session cookie MUST be invalid (`GET /api/auth/me` returns `401 unauthenticated`), the person MUST NOT be able to log in with the old identifier (`POST /api/auth/face-login` returns `401 auth_failed` indistinguishable from a never-enrolled identifier per spec 003), and no `User`, `FaceTemplate`, or `AuthSession` rows for that `userId` MUST remain in PostgreSQL (Constitution Principles V/VI, PRD §12).
- **FR-010**: The frontend MUST render a keyboard-accessible "Eliminar mis datos" button on `/dashboard` that, on press, shows a confirmation dialog explaining the action is permanent; on confirm, it MUST call `DELETE /api/users/{userId}/face-data` with the session cookie and the session's `userId`, disable the button during the in-flight request, and on `200` success clear all session state, release the camera stream, discard held analysis results, and navigate to `/` (PRD §8, FR-017, PRD §10).
- **FR-011**: On a `500 internal_error` deletion response, the frontend MUST show an actionable error with a retry option that does not require a full page reload and re-enable the button; on `401 unauthenticated` it MUST transition to the unauthenticated state (redirect to `/login`); on cancel of the confirmation dialog it MUST make no request (FR-015, PRD §10).
- **FR-012**: The deletion button, confirmation dialog, and all state communication MUST be keyboard-accessible with descriptive accessible names and MUST NOT rely exclusively on color to communicate state (PRD §10).
- **FR-013**: The domain orchestration of face-data deletion MUST depend only on the ports (user repository, face-template repository, session manager, image storage) and MUST NOT import any concrete web framework, DB driver, or filesystem adapter directly (Constitution Principle VII).
- **FR-014**: The deletion operation MUST NOT invoke any ML port (detector, embedder, mood estimator, age estimator); it is a pure data/infrastructure operation (Constitution Principle VII, scope boundary — real ML is Fase 5).
- **FR-015**: An automated test suite MUST cover deletion unit (authorization rule, deletion ordering, error mapping), integration (real endpoint + real PostgreSQL + real filesystem adapter — happy path, each authorization failure, `404 not_found`, DB-failure rollback, best-effort filesystem-failure), and contract (`200` shape, status codes `200`/`401`/`403`/`404`/`422`/`500`, pinned error body) cases, with the domain portions running without GPU, network, or real models (PRD §15, Constitution Quality Gates §5/§6/§7).
- **FR-016**: No image, embedding, or biometric response MUST appear in application logs; observability is limited to structured JSON logs (duration, type, status of the deletion operation, and a warning if filesystem cleanup fails) consistent with specs 001-004 and Constitution Principle VIII (PRD §12, §13). No audit log or immutable event store is required (Principle VIII — no traceability guarantee).
- **FR-017**: Soft-delete, retention policies, rate limiting, an admin panel/UI, and an audit trail are explicitly out of scope for this spec (PRD §4 non-goals, Constitution Principle VIII, Principle I — YAGNI).

### Key Entities *(include if feature involves data)*

- **User (from spec 002)**: The registered person being deleted. Hard-deleted in this spec (no `status = disabled` soft-delete). No new attributes; the row is removed from PostgreSQL.
- **FaceTemplate (from spec 002)**: The stored facial embedding for the user. Deleted (all rows for the `userId`) in the same transaction as the `User`. No new attributes.
- **AuthSession (from spec 003)**: The user's authenticated sessions. All rows for the `userId` are deleted in the same transaction, invalidating every session (not just the current one). No new attributes.
- **Filesystem Image Folder (from spec 002, Constitution Principle V)**: The `usuarios/<user-id>/` directory and its `pictures.jpg`. Deleted on a best-effort basis after the DB commit. No new entity; the image-storage port's delete-folder capability is exercised.
- **Deletion Result (transient view model)**: The response `{userId, status: "deleted"}` returned to the frontend. Not persisted; no new persistent entity is introduced in this spec.

## Assumptions

- This spec builds directly on specs 001-004: the runnable stack, the four views, the seven HTTP contract endpoints (here `DELETE /api/users/{userId}/face-data` is filled with real logic; the other six endpoints are already implemented per specs 002-004), the domain entities (`User`, `FaceTemplate`, `AuthSession`), the hexagonal ports (user repository, face-template repository, session manager, image storage — all with the capabilities needed for deletion; if a delete-by-userId capability is not yet present on a repository port it is added as a port method with a PostgreSQL adapter implementation, not a new port), the mock adapters, the PostgreSQL schema/migrations, the filesystem image-storage adapter (Constitution Principle V), the real session validation (`require_valid_session`), the `ProtectedRoute`, the dashboard with mood/age buttons and "Cerrar sesión" (spec 004), and the pinned error body shape `{"error": {"code": "...", "message": "..."}}` are all assumed to exist and be reused, not re-created.
- The technology stack is fixed by the Constitution (Principle III / Technology Stack table): backend in Python with FastAPI, frontend in React with Vite, PostgreSQL for persistence, Docker Compose for orchestration. These are project-level decisions, not ad hoc implementation choices, and are assumed settled for this spec.
- The deletion response body is `{"userId": "<echoed UUID v4>", "status": "deleted"}` with `200 OK` and a cleared session cookie, matching the spec 001 contract stub and PRD §8. This is the pinned contract.
- The error body shape is the spec-002-pinned `{"error": {"code": "...", "message": "..."}}` flat shape, reused verbatim. Machine codes are stable strings (`unauthenticated`, `forbidden`, `not_found`, `internal_error`). Status-code mapping is pinned: `401` exclusively for `unauthenticated` (session-gating); `403` for `forbidden` (authenticated but not the owner); `404` for `not_found` (user does not exist); `422` for malformed UUID (FastAPI path validation); `500` for recoverable `internal_error`. Human messages are actionable per FR-015 and reveal no internal details. The `403 forbidden` code is intentionally revealing (the caller is already authenticated; the demo narrative is "you can only delete your own data"), unlike login's non-revealing `auth_failed` (spec 003).
- Hard delete is chosen over soft-delete (`status = disabled`) per Constitution Principle I (demo-first) and YAGNI: a hard delete makes "the user is gone" literally true, makes the "right to be forgotten" narrative unambiguous, and requires no retention/disabled-state handling. Soft-delete, retention policies, and audit trails are explicitly out of scope (Principle VIII — no traceability guarantee; FR-017).
- The authorization model is demo-grade: the session's `userId` must match the path `userId` (the authenticated person deletes their own data). There is no admin panel (PRD §4 non-goal) and no admin role/token (Principle VIII — no security guarantee). This blocks the obvious abuse (deleting someone else's data) without introducing production-grade authorization. It is a reasonable default given the demo scope and the absence of an admin UI.
- The endpoint evaluates conditions in the order: path-parameter validation (`422`) → session validation (`401 unauthenticated`) → authorization check (`403 forbidden`) → user lookup (`404 not_found`) → deletion operation → cookie clear → `200` response. This ordering ensures a malformed path is rejected before any session/authorization work, and an unauthenticated caller is rejected before the authorization check, consistent with specs 002/003.
- The DB deletion is a single PostgreSQL transaction: `FaceTemplate` rows first, then `AuthSession` rows, then the `User` row (dependents before parent), then commit. On failure, the transaction rolls back and the endpoint returns `500 internal_error` with no partial DB state. This ordering respects foreign-key dependencies and is a reasonable default.
- The filesystem cleanup (`usuarios/<user-id>/` and `pictures.jpg`) is best-effort after the DB commit: if the folder is absent or deletion fails, the endpoint still returns `200` and logs a structured warning. The DB is the source of truth for login (no `FaceTemplate` → no login), so an orphaned image folder is a minor demo inconsistency, not a functional failure. A two-phase commit across DB + filesystem is deliberately not added (Constitution Principle I — demo-first; YAGNI).
- The backend clears the session cookie on the `200` deletion response because the current `AuthSession` is among the rows deleted. The frontend also clears its in-memory session state. This is consistent with spec 003's logout cookie-clearing behavior.
- The person is redirected to `/` (the welcome page) after deleting their own data, distinct from logout's redirect to `/login`: after deletion there is no profile to log in with, so the welcome/onboarding entry point is the coherent destination. The frontend releases the camera stream and discards held mood/age results on this transition (they were transient per spec 004).
- A frontend "Eliminar mis datos" button with a confirmation dialog is included so the "right to be forgotten" is a user-facing demo operation (FR-017 — "durante la demo"), not just a backend primitive. The confirmation prevents accidental destructive deletion; it is a lightweight native confirm, not a full settings page (Principle I — demo-first). This is a reasonable default given the feature scope explicitly includes "frontend logout-after-deletion handling".
- Deletion is not specially idempotent: a valid session guarantees the user exists, so the first call succeeds and destroys the session; a second call with the now-deleted session receives `401 unauthenticated`. No idempotent `200`-on-already-deleted semantics are added (YAGNI).
- The deletion operation invokes no ML port (detector/embedder/mood/age); it is a pure data/infrastructure operation. The mock vs real model distinction is irrelevant to this spec; Fase 5 model work is out of scope (FR-014).
- Age estimation (spec 005), real ML models (Fase 5), continuous video analysis, rate limiting, liveness/anti-spoofing, soft-delete/retention, audit log, and an admin panel/UI are explicitly out of scope for this spec.
- Observability in this spec is limited to structured JSON logs (duration, type, status of the deletion operation, and a warning if filesystem cleanup fails) with no images, embeddings, or biometric responses logged, consistent with specs 001-004 and Constitution Principle VIII (no traceability guarantee). No audit log or immutable event store is required.
- The frontend camera stream lifecycle (acquired on dashboard mount, released on unmount) from spec 004 is reused; deletion triggers a dashboard unmount (navigation to `/`), so the stream is released as part of the post-deletion transition. Tests mock `MediaDevices` lifecycle and the fetch layer for deletion responses, as anticipated by PRD §15.
- The session validation, `ProtectedRoute`, "Cerrar sesión" button, mood/age buttons, and dashboard layout from specs 003/004 are reused unchanged; this spec adds the "Eliminar mis datos" button, confirmation dialog, and the post-deletion logout-and-redirect-to-`/` handling to the dashboard.
